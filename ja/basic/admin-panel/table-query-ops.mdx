<Tip>セルフホストのBusinessプラン以上で利用できます</Tip>

パス：システム管理 → テーブル運用 → 検索とインデックス

大規模なテーブルでビュー、フィルター、リレーション、検索が遅くなった場合は、**検索とインデックス**を使用します。Teableはバックグラウンドでクエリの負荷を観測し、テーブルごとに現状をまとめます。現在どの方式で検索しているか、どのフィールドがカバーされているか、どの物理インデックスがあるか、直近の低速クエリはどれくらいかが分かります。インスタンス管理者は、ここで検索カバレッジの設定、インデックスの作成、実行結果の追跡を行います。

<Info>検索設定とインデックスの変更はバックグラウンドで非同期に実行されます。送信後は**履歴**で結果を確認してください。</Info>

<Info>クエリの観測は既定で無効です。バックエンドで `V2_TABLE_QUERY_OPS_ENABLED` を `true` に設定して再起動すると、観測データの収集が始まります。</Info>

## 対応が必要なテーブルを探す

ページを開くとテーブル一覧が表示されます。上部の状態ボタンにはそれぞれの件数が付いており、一覧を絞り込めます。

| 状態 | 意味 |
| --- | --- |
| **すべてのテーブル** | インスタンス内の削除されていないすべてのテーブル。クエリの観測データがないテーブルも含みます。 |
| **要対応** | 低速クエリ、タイムアウト、未処理の推奨事項があるテーブル、または検索を設定済みでも未使用か、対応する全フィールドをカバーしていないテーブル。ここから確認します。 |
| **インデックス検索** | インデックスのメタデータが公開済みかつ利用可能で、ランタイムスイッチもオンのテーブル。検索が実際にインデックスを使います。|
| **設定済みですが未使用** | 件数は設定済みでも全件走査にフォールバックするテーブル数です。クリックすると検索を設定済みの全テーブルが表示され、設定と実際の使用状況を比較できます。 |
| **未設定** | 検索カバレッジがまだないテーブル。|
| **利用不可** | 現在インデックス検索を利用できないテーブル。行に理由が表示されます。|

検索ボックスでは、テーブル、プロジェクト、スペースの名前とIDを指定できます。並べ替えは**低速クエリが多い順**または**テーブル名**です。**観測期間**は直近1時間または24時間から選べ、一覧の観測値はすべてこの期間に従います。観測データの保持期間は2日間で、それより古いものは一覧に表示されません。

各行には、テーブルの推定行数とサイズ、期間内のリクエスト数と低速クエリ数、現在の検索方式とフィールドのカバー状況、フィルター/ソート用インデックスの数、未処理の推奨事項と実行中タスクの件数が表示されます。テーブル名をクリックすると詳細が開きます。

上部の**テーブルを選択**でテーブルを直接切り替えることもできます。**複雑さ**や**スキーマの整合性**への切り替えでは選択が維持されます。**計算の更新**にはインスタンス全体のキューが表示されます。

## インデックスの状態を読む

テーブル一覧と詳細では、検索方式の横にそのテーブルのインデックス状態が表示されます。

| 状態 | 意味 | 次の対応 |
| --- | --- | --- |
| **未設定** | 保存された検索設定もインデックスのメタデータもありません。| インデックス検索が必要なら**検索を設定**を選びます。|
| **公開待ち** | 設定は保存済みで、インデックスの公開が完了していません。| **履歴**でタスクが実行中か確認します。|
| **準備完了** | インデックスのメタデータが公開済みで利用できます。| 実際の検索方式とランタイムスイッチを確認し、インデックスが使用されているか判断します。 |
| **メタデータが利用不可** | インデックスのメタデータに問題があり、検索に使用できません。| **フィールド選択の更新 / 再構築**をもう一度実行します。|

状態の下には次の2行が表示されることがあります。**設定済み：pg_bigm / pg_trgm**は、保存されたプロバイダーが現在の検索方式と異なることを示します。**インデックス検索のランタイムスイッチ：オフ**は、インデックスは準備できているがランタイムが無効で、検索が`ILIKE`のままであることを示します。

ページ上部の通知に、検索インデックスを設定済みなのに機能していないテーブルが表示された場合、それらのテーブルの検索は`ILIKE`にフォールバックします。タスクワーカーがオフであることも表示されている場合は、バックエンドで`V2_TABLE_QUERY_OPS_TASK_WORKER_ENABLED`を`true`に設定して再起動すると、インデックスを再構築できるようになります。

<Info>インデックスが公開済みでも、すべての検索がインデックスを使うわけではありません。検索語が短い場合やカバレッジ外のフィールドでは`ILIKE`にフォールバックします。このページが示すのはインデックスの現状であり、直近のリクエストがインデックスを使ったことの証明ではありません。</Info>

## 検索カバレッジを設定する

**検索**タブには、そのテーブルの現在の検索方式、カバー済みフィールド数、各フィールドの**有効なカバレッジ**が表示されます。**未カバーのフィールドを表示**を使うと、まだ含まれていないフィールドだけに絞り込めます。**対象外**と表示されたフィールドは、部分一致検索インデックスには使用できません。

<Info>有効なカバレッジには、インデックスのメタデータが公開済みかつ利用可能で、ランタイムスイッチがオンであることが必要です。設定を保存しただけではカバレッジに数えられません。カバレッジは明示的に指定するため、あとから追加したフィールドは自動では含まれません。テーブルを設定し直して取り込んでください。</Info>

未設定のテーブルでは**検索を設定**、設定済みのテーブルでは**フィールド選択の更新 / 再構築**を選びます。再構築の場合、ダイアログには前回保存したプロバイダーとフィールド選択が入った状態で開きます。ダイアログでは次の項目を指定します。

| 項目 | 入力内容 |
| --- | --- |
| **検索プロバイダー** | `pg_bigm`または`pg_trgm`。拡張機能が未導入の場合は、何が不足していて誰が対応できるかがダイアログに表示されます。|
| **代表的な検索語** | ユーザーが実際に検索しそうな語を入力します。部分一致のセマンティクス確認と実行計画の根拠収集に使われ、保存されることはありません。短すぎる場合は必要な最小文字数が表示されます。|
| **フィールド** | ユーザーが実際に検索するフィールドを選びます。列数の多いテーブルですべてを選ばないでください。全フィールドの検索ドキュメントを作るとコストが高くなります。|

**分析してドライラン**を実行すると、確定せずに変更を試算し、カバー対象のフィールド数、推定行数、実行計画の根拠の有無、新規作成または再構築による影響が表示されます。推定5万行以上のテーブルやサイズが不明なテーブルでは、メンテナンスウィンドウの確認チェックも必要です。内容を確認したら**確認してタスクを登録**を選びます。

<Warning>検索カバレッジの作成や再構築では、検索用の列とGINインデックスが生成されます。テーブル全体の書き換えとロックが発生する可能性があり、その間はインデックス検索が一時的に中断されます。メンテナンスウィンドウ内で実施してください。</Warning>

ダイアログに表示されるのはタスクの受付結果であり、実行結果ではありません。ダイアログを閉じ、**履歴**で進捗を追ってください。同じ変更を再送信しても、既存のタスクが返されます。

## フィルター/ソート用インデックスを管理する

**インデックス**タブには、フィルター・ソート用とシステム用のインデックスが表示され、有効性、管理状態、サイズ、定義を確認できます。部分一致検索のインデックスは**検索**タブで個別に確認します。

その**保留中の操作**には、システムが提示したインデックスの推奨事項と、実行計画の根拠の有無が表示されます。**インデックス作成を確認**では、提案されたインデックス、実行先のデータベース、根拠を確認できます。確定すると、Teableは`CREATE INDEX CONCURRENTLY`を非同期で実行します。大規模なテーブルやサイズが不明なテーブルでは、ここでもメンテナンスウィンドウの確認が必要です。

<Info>このページからインデックスを削除することはできません。非管理インデックスやシステムインデックスは制約や他のクエリに使われている可能性があるため、削除の対象外です。</Info>

## 個別のクエリを診断する

特定のテーブルが遅いと報告されたものの、該当する推奨事項がない場合は、**診断**タブを開いて**クエリを分析**を選びます。分析は保存済みのクエリ形状と利用可能な実行計画の根拠を読み取るだけで、インデックスは作成しません。

結果は、**実行計画に裏付けられたインデックス改善余地あり**、**利用可能な実行計画ではインデックス改善余地を確認できず**、**根拠不足**のいずれかです。根拠不足はシーケンシャルスキャンが起きた証拠にはなりません。低速クエリの観測だけでは、アクセスパスに問題があるとは言えないためです。その下には、対象のクエリごとに、実際のトラフィック由来か保存済みビュー設定由来かと、提案インデックス適用前後の推定プランコスト（ミリ秒ではなくプランコスト）が表示されます。

## 実行結果を追う

**履歴**タブは3つの部分で構成されています。

- **タスク**：このテーブルのバックグラウンドタスク。状態、試行回数、タスク種別、失敗理由が表示されます。失敗したあとに最終的に成功したタスクでは、エラーが過去の試行として表示されます。
- **検索設定履歴**：過去の検索カバレッジ設定のプロバイダー、状態、フィールド一覧。
- **推奨事項の履歴**：承認、却下、置き換えとなった推奨事項。

履歴は最新の一定件数のみ読み込まれます。それを超える場合は、一覧の上に総件数が表示されます。

<Info>テーブルに待機中または実行中のタスクがある間は、検索の設定とインデックス作成のボタンは無効になります。タスクの完了を待ってから操作してください。</Info>

## 変更の影響を評価する

レコードの更新により、関連レコードを通じて数式、ルックアップ、ロールアップの追加計算が発生することがあります。一括書き込み、フィールド変換、削除が大量のデータに影響するか確認するには、**複雑さ**で対象テーブルを選択します。検索とインデックスのテーブル詳細から**複雑さを評価**をクリックすることもできます。

**影響マトリクス**には、フィールドごとの更新、削除、変換の推定値と、レコードの作成・削除の推定値が表示されます。左側の点は典型的な場合、塗りは最悪の場合を表します。セルをクリックすると、対象行数、伝播経路、制限、推奨事項を確認できます。**高**や**重大**の変更から確認し、バッチを小さくするか計算の依存関係を調整するか判断してください。

**推定設定**で、**変更あたりのレコード数**を一度に送信する予定の件数に設定します。空欄の場合は1件として推定します。**カタログ統計を使用**は既定で有効で、データベースのテーブル規模とリンク数を読み取り、推定精度を高めます。

<Info>評価では構造と統計のみを読み取り、レコードやフィールドを変更しません。実際の処理時間を示すものでもありません。**未推定**、または推定品質が**部分**や**打ち切り**の場合は、制限を確認して不足情報を補ってから判断してください。推定値がないことは、リスクがないことを意味しません。</Info>
