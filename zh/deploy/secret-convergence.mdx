<Tip>文中用到的两个管理页面适用于私有化部署 Business 及以上版本</Tip>

Teable 的服务端密钥都可以由 `SECRET_KEY` 给出：JWT、会话和各类加密密钥在没有单独设置时，直接使用它或由它派生。应用自己只需要两个密钥：

- `SECRET_KEY`：根密钥。
- `SANDBOX_JWT_SECRET`：沙箱执行令牌的签名密钥。沙箱运行的是用户的脚本，不持有根密钥，所以它不跟随 `SECRET_KEY`。

其余专属变量（`BACKEND_JWT_SECRET`、`BACKEND_SESSION_SECRET`、各个 `*_ENCRYPTION_*` 等）不建议再设置，以后的版本可能不再读取其中的大部分。本文说明已有实例怎样改成只用这两个密钥，同时不丢失已有数据。

全新部署不需要本文的步骤：按[环境变量](/zh/deploy/env#密钥与轮换)生成这两个密钥，其余变量不要设置即可（也不要写成空值）。

## 开始之前

- **先升级。** 把实例升级到最新版本，再开始下面的步骤。步骤要用到系统管理里的「加密密钥收敛」和「JWT 凭据」两个页面，系统管理里看不到它们，说明版本过旧，或者版本低于 Business。
- **备份。** 备份数据库和全部环境变量。重加密之后，数据只能用当前密钥解开。
- **安排维护窗口。** 整个过程要重启实例；更换会话密钥时，用户需要重新登录。
- **多副本一起换。** 所有副本和 worker 都要用同一份新配置重启，之后才能执行重加密。仍在旧配置上的副本读不出重写后的数据。

## 第一步：查看现状

实例还在用公开的内置默认值时，启动日志会列出缺少的密钥，实例管理员在 **系统管理 → 实例设置** 的「待配置项」里也会看到「服务端密钥」提醒。启动日志还会给出一段把当前取值固定下来的变量，按本文操作不需要添加它；已经添加过的实例，这些变量会作为带「公开值」标记的专属变量出现在页面上。

要看完整的配置，以实例管理员身份打开 **系统管理 → 加密密钥收敛 → 服务端密钥**。页面列出 `SECRET_KEY`、`SANDBOX_JWT_SECRET`，以及还设着专属变量或 `_OLD` 变量的密钥。没列出的密钥都跟随 `SECRET_KEY`，不需要处理。各列的含义见[加密密钥收敛](/zh/basic/admin-panel/key-convergence#server-secrets)。

按页面的显示判断属于哪些情况，可能同时有几种：

| 页面显示 | 说明 | 接下来 |
|---|---|---|
| 只有 `SECRET_KEY` 和 `SANDBOX_JWT_SECRET` 两行，都没有「公开值」标记 | 已经是目标状态 | 不用操作 |
| `SECRET_KEY` 没有「公开值」标记，另外列出了专属变量 | 根密钥没问题，还有专属变量要去掉 | [去掉专属变量](#remove-dedicated-variables) |
| `SECRET_KEY` 显示未设置，或带「公开值」标记 | 实例在用公开的内置默认值 | [换上自己的 SECRET_KEY](#own-secret-key) |
| `SANDBOX_JWT_SECRET` 带「公开值」标记 | 沙箱密钥还是公开的默认值 | 用 `openssl rand -base64 32` 生成一个值，设置到应用上；运行了沙箱服务的，沙箱服务也要设置同一个值，然后重启。没有存量数据依赖它 |
| 有些行只是因为还设着 `_OLD` 变量才列出 | 旧值还在保留期内 | 到了[下表](#old-value-retention)允许的时间再逐个删除 |

<Warning>从文档或示例文件里照抄的值和内置默认值一样是公开的，但页面识别不出来。[Docker 部署](/zh/deploy/docker)页的模板里写的是 `SECRET_KEY=replace_this_secret_key`：实例如果还在用这个值，要把 `SECRET_KEY` 当作公开值，按[换上自己的 SECRET_KEY](#own-secret-key)处理。</Warning>

## 去掉专属变量 {#remove-dedicated-variables}

对「取值来源」是「专属变量」的每一行（`SECRET_KEY` 和 `SANDBOX_JWT_SECRET` 本身除外），看最后一列「与只设 SECRET_KEY 时相同」：

- **相同**：直接删除这个变量。取值不变，不影响任何数据。
- **不同**：把它现在的值改放到同名的 `_OLD` 变量里（例如 `BACKEND_AI_CONFIG_ENCRYPTION_SECRET_OLD`），再删除它本身。`_OLD` 只用来验证或解密旧数据，新数据一律使用 `SECRET_KEY`。key 和 iv 成对的变量，两个 `_OLD` 必须一起设置。[下表](#old-value-retention)里没有列出的变量没有对应的 `_OLD`，直接删除即可；带「待废弃」标签的除外，见表格下方的说明。

每个 `_OLD` 变量只能保存一代旧值。如果环境变量里已经有 `_OLD`（例如之前换过一次密钥），先完成重加密并删掉它，再开始新的一轮；否则仍用更早一代密钥加密的数据会解不开，需要重新填写。

所有变量可以放在同一次变更里处理：

1. 停止实例，按上面的规则修改环境变量，然后启动全部副本。
2. 打开[库内密文](/zh/basic/admin-panel/key-convergence#stored-ciphertexts)标签，点 **试运行**。「无法解密」一列应该全是 0；不是 0 说明缺了某个 `_OLD`，先补上再继续。
3. 点 **重加密**，完成后再试运行一次。「待重加密」和「无法解密」都是 0，库内密文就已经全部换到 `SECRET_KEY` 下。
4. 如果更换了 JWT 签名密钥，并且实例里有 App Builder 应用：打开 [JWT 凭据](/zh/basic/admin-panel/jwt-credentials)，在「需处理」里刷新所有应用的凭据。
5. 抽查登录、个人访问令牌调用、AI 功能、自动化里的第三方凭据和已发布的应用。
6. 按下表的时间删除各个 `_OLD` 变量，每次删除后重启。

### 各个旧值要保留多久 {#old-value-retention}

| 变量 | `_OLD` 的作用 | 什么时候可以删 `_OLD` | 不设 `_OLD` 直接切换的后果 |
|---|---|---|---|
| `BACKEND_ENV_VARIABLE_SECRET`、`BACKEND_AI_CONFIG_ENCRYPTION_SECRET`、`BACKEND_THIRD_PARTY_CREDENTIAL_ENCRYPTION_SECRET` | 解开库里用旧值加密的应用环境变量、AI 供应商密钥和第三方凭据 | 重加密完成、试运行两列都是 0 之后。第三方凭据的密钥另见表格下方关于自动化的说明 | 这些数据解不开。必须设置 |
| `BACKEND_DATA_DB_URL_ENCRYPTION_SECRET_OLD`、`BACKEND_DATA_DB_URL_ENCRYPTION_KEY_OLD` / `IV_OLD`（只有 `_OLD` 形式） | 解开用旧值加密的[数据库租户](/zh/basic/admin-panel/database-tenant)连接串 | 重加密完成、试运行两列都是 0 之后 | 这些连接串解不开。必须设置 |
| `BACKEND_JWT_SECRET` | 验证旧密钥签发的令牌 | [JWT 凭据](/zh/basic/admin-panel/jwt-credentials)里「需处理」「刷新失败」「线上凭据未更新」都为空，并且已过 30 天（第三方应用授权的刷新令牌有效期） | 带密码的分享链接需要重新输入密码，第三方应用需要重新授权；应用在刷新凭据之前无法访问 Teable |
| `BACKEND_SESSION_SECRET` | 验证旧的登录会话 | 过了一个会话有效期之后（`BACKEND_SESSION_EXPIRES_IN`，默认 7 天） | 所有用户重新登录 |
| `BACKEND_INVITATION_SECRET` | 验证已发出的邀请链接 | 邮件邀请一个月后过期。在空间或项目里创建的邀请链接不会过期：删掉 `_OLD` 之后它们仍然列在页面上，但已经不能用，需要删除后重新创建 | 还没接受的邮件邀请和已有的邀请链接失效，需要重新邀请、重新创建链接 |
| `BACKEND_MAIL_ENCRYPTION_KEY` / `IV` | 验证已发出邮件里的退订链接 | 自行决定。退订链接不过期，删除后旧邮件里的链接失效 | 旧邮件里的退订链接失效 |
| `BACKEND_ACCESS_TOKEN_ENCRYPTION_KEY` / `IV` | 让用旧 key/iv 签发的个人访问令牌继续可用 | [个人访问令牌](/zh/basic/admin-panel/key-convergence#personal-access-tokens)标签里，依赖旧密钥的令牌清零之后 | 这些个人访问令牌立即停用，持有者需要重新生成。旧版本用这组 key/iv 加密保存的数据库租户连接串也会解不开 |
| `BACKEND_STORAGE_ENCRYPTION_KEY` / `IV` | 不需要 | — | 已签发的本地存储附件链接失效，刷新页面后重新获取 |

运行中的自动化使用的是它的步骤的一份副本，重加密不会改写这份副本。把邮箱密码或 Webhook 密钥直接保存在步骤里的自动化，仍然要用旧值才能读出它们。删除 `BACKEND_THIRD_PARTY_CREDENTIAL_ENCRYPTION_SECRET_OLD` 之前，先编辑这些自动化并点 **更新**，让它们改用重加密之后的步骤。只有旧值不是公开值时才需要这样做：旧值是公开值时，这些凭据原本就没有加密。

`BACKEND_DATA_DB_URL_ENCRYPTION_KEY` / `IV` 在页面上带「待废弃」标签。它们只用于旧格式的[数据库租户](/zh/basic/admin-panel/database-tenant)连接串：先完成上面的重加密（连接串会改写成由 `SECRET_KEY` 保护的新格式），再直接删除这两个变量，不需要设置 `_OLD`。

<Warning>不要把公开的值或已经泄露的值放进 `BACKEND_JWT_SECRET_OLD` 或 `BACKEND_SESSION_SECRET_OLD`。`_OLD` 里的值仍然被接受，放进去等于继续接受用它伪造的令牌和会话。这种情况直接切换，让用户重新登录。</Warning>

## 换上自己的 SECRET_KEY {#own-secret-key}

实例没有设置 `SECRET_KEY`，或者它仍是公开的默认值时，跟随它的密钥用的都是公开值。换上自己的 `SECRET_KEY` 会让这些密钥一起变化，所以要先把旧值放进 `_OLD`，让已有数据还能解开。

1. 生成新的根密钥：

   ```bash
   openssl rand -base64 32
   ```

2. 准备 `_OLD` 变量。按实例之前的状态选择一列；页面上列着某个密钥的专属变量时，跳过它对应的那一行，因为它的取值不随 `SECRET_KEY` 变化：

   | 变量 | 之前没有设置 `SECRET_KEY` | 之前设置过 `SECRET_KEY`，现在要换掉 |
   |---|---|---|
   | `BACKEND_ENV_VARIABLE_SECRET_OLD` | `defaultSecretKey` | 旧的 `SECRET_KEY` |
   | `BACKEND_AI_CONFIG_ENCRYPTION_SECRET_OLD` | `defaultSecretKey` | 旧的 `SECRET_KEY` |
   | `BACKEND_THIRD_PARTY_CREDENTIAL_ENCRYPTION_SECRET_OLD` | 不需要：这些凭据之前没有加密，重加密时会被加密 | 旧的 `SECRET_KEY` |
   | `BACKEND_INVITATION_SECRET_OLD`（可选，保留已发出的邀请链接） | `defaultSecretKey` | 旧的 `SECRET_KEY` |
   | `BACKEND_ACCESS_TOKEN_ENCRYPTION_KEY_OLD` / `IV_OLD`（保留已签发的个人访问令牌） | 不需要：内置的旧值会自动保留，只用来解密 | 由旧的 `SECRET_KEY` 派生，见下面的命令 |
   | `BACKEND_MAIL_ENCRYPTION_KEY_OLD` / `IV_OLD`（可选，保留已发出邮件里的退订链接） | 不需要：同上 | 由旧的 `SECRET_KEY` 派生，见下面的命令 |
   | `BACKEND_DATA_DB_URL_ENCRYPTION_SECRET_OLD`（用了数据库租户时） | 不需要 | 旧的 `SECRET_KEY` |
   | `BACKEND_DATA_DB_URL_ENCRYPTION_KEY_OLD` / `IV_OLD`（用了数据库租户，并且没有单独设置过这一对时） | `ed333d03ac334ea2` / `3c50b81e61cb7f52` | 由旧的 `SECRET_KEY` 派生，见下面的命令 |
   | `BACKEND_JWT_SECRET_OLD`、`BACKEND_SESSION_SECRET_OLD` | 不设置：旧值是公开的 | 只有旧值没有公开、没有泄露时才设置 |

   最后一列里「由旧的 `SECRET_KEY` 派生」的值是 SHA-256 十六进制的前 16 位，算法见下面的 [Docker Compose 示例](#docker-compose-examples)。

3. 停止实例，设置新的 `SECRET_KEY` 和上面的 `_OLD` 变量，同时确认已经设置 `SANDBOX_JWT_SECRET`（后端和沙箱服务用同一个值），然后启动全部副本。
4. 之后的步骤和[去掉专属变量](#remove-dedicated-variables)的第 2 步到第 6 步相同：试运行、重加密、刷新应用凭据、抽查、按时间删除 `_OLD`。没有设置 `BACKEND_JWT_SECRET_OLD` 时，应用在刷新凭据之前无法访问 Teable，启动后请尽快在 [JWT 凭据](/zh/basic/admin-panel/jwt-credentials)里处理。

### Docker Compose 的 `.env` 示例 {#docker-compose-examples}

Docker Compose 部署可以在部署目录执行下面其中一段，把第 2 步和第 3 步里新的 `SECRET_KEY` 和各个 `_OLD` 变量写进 `.env`。执行前先停止实例并备份 `.env`，执行后用 `docker compose up -d` 启动。`.env` 的状态和预期不符时（例如里面已经有 `_OLD` 变量），脚本会给出提示，不做任何修改。脚本会写入表里的全部 `_OLD`：页面上列着其中某个密钥的专属变量时，启动实例之前先把这个密钥的 `_OLD` 那一行从 `.env` 里删掉。其他部署方式，把同样的变量加到 Teable 应用的环境变量里。使用[全功能部署套件](https://github.com/teableio/teable-deployment)的，变量的位置和生成方式不同，按套件里 Docker 或 Helm 部署说明（README）的「App secrets」一节操作。

    (
      set -eu
      if grep -Eq '^[A-Z_]+_OLD=' .env; then

        echo "Run the block above first, and only once: nothing changed" >&2

    BACKEND_JWT_SECRET_OLD=${raw}
    BACKEND_SESSION_SECRET_OLD=${raw}
    EOF
    )

### 换完之后

换上新的 `SECRET_KEY` 之后：

- 没有设置 `BACKEND_JWT_SECRET_OLD` 和 `BACKEND_SESSION_SECRET_OLD` 时，所有人需要重新登录，访问带密码的分享链接需要重新输入密码。
- 没有设置 `BACKEND_INVITATION_SECRET_OLD` 时，还没接受的邮件邀请和已有的邀请链接失效，需要重新邀请、重新创建链接。
- 使用本地存储的，之前复制出去的附件链接失效；刷新页面后附件预览正常。
- 使用 [Docker 部署](/zh/deploy/docker)页 MinIO 方案的（`MINIO_SECRET_KEY=${SECRET_KEY}`），MinIO 的 root 密码会随 `SECRET_KEY` 一起更换，已有的文件和桶不受影响；之前签发的附件链接失效，刷新页面后恢复。
- 个人访问令牌、邮件退订链接、数据库租户的连接、AI 配置和应用环境变量继续可用。

如果页面上除了 `SECRET_KEY` 之外还列着专属变量，换完根密钥后再按[去掉专属变量](#remove-dedicated-variables)处理它们。专属变量有自己的值时不受 `SECRET_KEY` 变化的影响，所以上面不设置它对应的 `_OLD`：之后去掉这个专属变量时，`_OLD` 要用来保存它自己的值。

## 回滚

- **重加密之前**：把环境变量改回变更前的配置并重启即可。这期间保存的内容（凭据、AI 密钥、应用环境变量、新签发的令牌和会话）是按新配置写入的，回到旧配置后读不出来，重新切到新配置后恢复。
- **重加密之后**：不要回滚环境变量，也不要降级镜像。重写后的数据只能用当前密钥解开；确实需要回退时，从变更前的备份恢复数据库和环境变量。

## 常见问题

<AccordionGroup>
  <Accordion title="删掉专属变量之后，怎么确认它已经跟随 SECRET_KEY？">
    重启后再看「服务端密钥」标签：顶部「还设着的专属变量」数量减少。这个变量设着 `_OLD` 时，它的行会保留到 `_OLD` 删除为止，「取值来源」变成「回落到 SECRET_KEY」或「由 SECRET_KEY 派生」；没有设 `_OLD` 时，这一行不再出现。
  </Accordion>
  <Accordion title="试运行里「无法解密」不是 0 怎么办？">
    这些行用当前密钥和已配置的 `_OLD` 都解不开，重加密会跳过它们、保持原样。通常是缺了某个旧值：对照页面给出的表名和行 ID，把加密它们时使用的值放进对应的 `_OLD` 变量，重启后再试运行。
  </Accordion>
  <Accordion title="还想保留某个专属变量，只是要更换它的值怎么办？">
    把新值写进这个变量，把当前值移到同名的 `_OLD` 变量里。成对的 key 和 iv 要一起更换，两个 `_OLD` 也要成对设置，只设一半时服务无法启动。16 位的值用 `openssl rand -hex 8` 生成，其余用 `openssl rand -base64 32`。值已经泄露时不要放进 `_OLD`，直接换新。
  </Accordion>
  <Accordion title="实例里没有这两个管理页面怎么办？">
    社区版和低于 Business 的版本没有这两个页面。新部署不受影响；已有实例更换密钥时，把旧值留在对应的 `_OLD` 变量里，旧数据仍然可以读取。没有重加密，库里的数据在重新保存之前一直使用旧值，所以这些数据对应的 `_OLD` 变量要一直保留。
  </Accordion>
