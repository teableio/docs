<Tip>La page d’administration utilisée ici est disponible avec le forfait Business auto-hébergé et les forfaits supérieurs</Tip>

`SECRET_KEY` peut fournir tous les secrets du serveur dont Teable a besoin. Les JWT, les sessions et les différentes clés de chiffrement l’utilisent directement, ou utilisent une clé qui en est dérivée, dès lors qu’ils n’ont pas de variable qui leur est propre. L’application a besoin de deux secrets qui lui sont propres :

- `SECRET_KEY` : le secret racine.
- `SANDBOX_JWT_SECRET` : signe les jetons d’exécution du sandbox. Le sandbox exécute les scripts de vos utilisateurs et ne détient jamais le secret racine ; ce secret ne suit donc pas `SECRET_KEY`.

Il n’est plus recommandé de définir les autres variables dédiées (`BACKEND_JWT_SECRET`, `BACKEND_SESSION_SECRET`, les variables `*_ENCRYPTION_*`, etc.), et une version ultérieure pourrait cesser de lire la plupart d’entre elles. Cette page explique comment faire passer une instance existante à ces deux secrets sans perdre les données qu’elle contient déjà.

Une variable facultative fait exception : `BACKEND_STORED_CREDENTIAL_ENCRYPTION_SECRET` donne aux identifiants chiffrés dans la base de données leur propre secret racine. Voir [Un secret racine distinct pour les identifiants stockés](#stored-credential-root).

Un nouveau déploiement n’a besoin de rien de tout cela : générez les deux secrets comme indiqué dans [Variables d’environnement](/fr/deploy/env#secrets-and-rotation) et laissez les autres non définis.

<Warning>Une version ultérieure refusera de démarrer tant que `SECRET_KEY` n’est pas défini ou qu’il est encore la valeur par défaut publique. Si votre instance fonctionne ainsi, [passez à votre propre SECRET_KEY](#own-secret-key) avant de mettre à niveau vers cette version.</Warning>

## Avant de commencer

- **Mettez d’abord à niveau.** Amenez l’instance à la dernière version avant de commencer. Les étapes utilisent la page **Rotation des clés** de l’Administration système ; si l’Administration système ne l’affiche pas, la version est trop ancienne ou le forfait est inférieur à Business.
- **Sauvegardez.** Sauvegardez la base de données et toutes les variables d’environnement. Après un rechiffrement, les données ne s’ouvrent qu’avec la clé actuelle.
- **Prévoyez une fenêtre de maintenance.** L’instance redémarre en cours de route, et les utilisateurs doivent se reconnecter lorsque le secret de session change.
- **Modifiez tous les réplicas ensemble.** Tous les réplicas et tous les workers doivent redémarrer avec la même nouvelle configuration avant le rechiffrement. Un réplica resté sur l’ancienne configuration ne peut pas lire les données réécrites.

## Étape 1 : vérifier ce qui est défini

Tant qu’une instance fonctionne encore avec les valeurs par défaut intégrées, qui sont publiques, le journal de démarrage liste les secrets manquants, et les administrateurs d’instance voient un élément **Secrets du serveur** dans **Administration système → Paramètres d'instance**, dans le panneau **Configuration en attente**. Le journal de démarrage affiche aussi un bloc de variables qui fige les valeurs actuelles. Ce guide n’en a pas besoin ; sur une instance qui a déjà ajouté ce bloc, ces variables apparaissent sur la page comme des variables dédiées marquées **Valeur publique**.

Pour une vue complète, ouvrez **Administration système → Rotation des clés → Secrets du serveur** en tant qu’administrateur d’instance. Y figurent `SECRET_KEY`, `SANDBOX_JWT_SECRET` et chaque secret pour lequel une variable dédiée ou une variable `_OLD` est encore définie. Un secret qui n’y figure pas suit `SECRET_KEY` et ne demande aucune action. [Rotation des clés](/fr/basic/admin-panel/key-rotation#server-secrets) explique les colonnes.

Servez-vous de ce que la page affiche pour déterminer quels cas s’appliquent ; il peut y en avoir plusieurs :

| La page affiche | Ce que cela signifie | Suite |
|---|---|---|
| Uniquement les lignes `SECRET_KEY` et `SANDBOX_JWT_SECRET`, aucune des deux marquée **Valeur publique** | L’état cible est déjà atteint | Rien à faire |
| `SECRET_KEY` sans **Valeur publique**, plus des variables dédiées | Le secret racine est correct ; il reste des variables dédiées | [Supprimer les variables dédiées](#remove-dedicated-variables) |
| `SECRET_KEY` affiché comme non défini, ou marqué **Valeur publique** | L’instance fonctionne avec des valeurs par défaut intégrées, qui sont publiques | [Passer à votre propre SECRET_KEY](#own-secret-key) |
| `SANDBOX_JWT_SECRET` marqué **Valeur publique** | Le secret du sandbox est encore la valeur par défaut publique | Générez une valeur avec `openssl rand -base64 32`, définissez-la pour l’application et, si vous exécutez un service sandbox, pour ce service aussi, puis redémarrez. Aucune donnée stockée n’en dépend |
| Des lignes listées uniquement pour leurs variables `_OLD` | D’anciennes valeurs sont encore conservées | Supprimez chacune d’elles lorsque [le tableau ci-dessous](#old-value-retention) le permet |

<Warning>Une valeur copiée depuis la documentation ou un fichier d’exemple est aussi publique qu’une valeur par défaut intégrée, mais la page ne peut pas le détecter. Le modèle de la page [Déploiement Docker](/fr/deploy/docker) contient `SECRET_KEY=replace_this_secret_key` : si l’instance fonctionne encore avec cette valeur, considérez `SECRET_KEY` comme public et suivez [Passer à votre propre SECRET_KEY](#own-secret-key).</Warning>

## Supprimer les variables dédiées {#remove-dedicated-variables}

Pour chaque ligne dont **Valeur issue de** indique **Variable dédiée**, hormis `SECRET_KEY` et `SANDBOX_JWT_SECRET` eux-mêmes, regardez la dernière colonne, **Identique à SECRET_KEY seul** :

- **Identique** : supprimez la variable. La valeur ne change pas et aucune donnée n’est affectée.
- **Différent** : déplacez sa valeur actuelle dans la variable de même nom suivie de `_OLD` (par exemple `BACKEND_AI_CONFIG_ENCRYPTION_SECRET_OLD`), puis supprimez la variable elle-même. `_OLD` sert uniquement à vérifier ou à déchiffrer les données existantes ; tout ce qui est nouveau utilise `SECRET_KEY`. Pour une paire clé et iv, définissez les deux variables `_OLD` ensemble. Une variable que [le tableau ci-dessous](#old-value-retention) ne liste pas n’a pas de `_OLD` : supprimez-la telle quelle, sauf si la page lui attribue l’étiquette **Obsolète** (voir la note sous le tableau).

Chaque variable `_OLD` ne contient qu’une seule valeur précédente. Si l’environnement comporte déjà des variables `_OLD`, par exemple à la suite d’un changement antérieur, terminez le rechiffrement et supprimez-les avant de commencer un nouveau cycle. Sinon, les données encore chiffrées avec la valeur plus ancienne deviennent illisibles et doivent être saisies à nouveau.

Vous pouvez traiter toutes les variables en une seule modification :

1. Arrêtez l’instance, modifiez les variables d’environnement comme décrit ci-dessus, puis démarrez tous les réplicas.
2. Ouvrez l’onglet [Textes chiffrés stockés](/fr/basic/admin-panel/key-rotation#stored-ciphertexts) et cliquez sur **Dry-run** (simulation). La colonne **Indéchiffrable** doit être à 0 partout. Si ce n’est pas le cas, une valeur `_OLD` manque : ajoutez-la avant de continuer.
3. Cliquez sur **Rechiffrer**, puis lancez la simulation une fois de plus. Lorsque **À rechiffrer** et **Indéchiffrable** sont tous deux à 0, tous les textes chiffrés stockés sont sous `SECRET_KEY`.
4. Si le secret de signature JWT a changé et que l’instance comporte des applications App Builder, ouvrez [JWT credentials](/fr/basic/admin-panel/jwt-credentials) et actualisez les identifiants de chaque application figurant sous **Needs attention** (à traiter).
5. Vérifiez par sondage la connexion, un appel avec un jeton d’accès personnel, les fonctionnalités IA, les identifiants tiers dans les automatisations et les applications publiées.
6. Supprimez chaque variable `_OLD` lorsque le tableau ci-dessous le permet, en redémarrant après chaque suppression.

### Durée de conservation de chaque ancienne valeur {#old-value-retention}

| Variable | Rôle de `_OLD` | Quand vous pouvez supprimer `_OLD` | Basculer sans `_OLD` |
|---|---|---|---|
| `BACKEND_ENV_VARIABLE_SECRET`, `BACKEND_AI_CONFIG_ENCRYPTION_SECRET`, `BACKEND_THIRD_PARTY_CREDENTIAL_ENCRYPTION_SECRET` | Déchiffre les variables d’environnement des applications, les clés des fournisseurs d’IA et les identifiants tiers stockés avec l’ancienne valeur | Après le rechiffrement, une fois les deux colonnes de la simulation à 0. Pour le secret des identifiants tiers, voir la note sur les automatisations sous le tableau | Ces données ne peuvent pas être déchiffrées. Définissez-le toujours |
| `BACKEND_STORED_CREDENTIAL_ENCRYPTION_SECRET` | Déchiffre tout ce que la variable couvre et qui a été stocké avec l’ancienne valeur : variables d’environnement des applications, clés des fournisseurs d’IA, identifiants tiers et chaînes de connexion des locataires de base de données | Après le rechiffrement, une fois les deux colonnes de la simulation à 0. La note sur les automatisations sous le tableau s’applique ici aussi | Ces données ne peuvent pas être déchiffrées. Définissez-le toujours |
| `BACKEND_DATA_DB_URL_ENCRYPTION_SECRET` | Déchiffre les chaînes de connexion des [locataires de base de données](/fr/basic/admin-panel/database-tenant) stockées avec l’ancienne valeur | Après le rechiffrement, une fois les deux colonnes de la simulation à 0 | Ces données ne peuvent pas être déchiffrées. Définissez-le toujours |
| `BACKEND_DATA_DB_URL_ENCRYPTION_KEY` / `IV` | Déchiffrent les chaînes de connexion des [locataires de base de données](/fr/basic/admin-panel/database-tenant) stockées avec l’ancienne valeur | Après le rechiffrement, une fois les deux colonnes de la simulation à 0 | Ces chaînes de connexion ne peuvent pas être déchiffrées. Définissez-les toujours |
| `BACKEND_JWT_SECRET` | Vérifie les jetons signés avec l’ancien secret | Lorsque **Needs attention**, **Refresh failed** (échec de l’actualisation) et **Live credentials outdated** (identifiants en ligne obsolètes) sont tous vides dans [JWT credentials](/fr/basic/admin-panel/jwt-credentials), et que 30 jours se sont écoulés (la durée de vie des jetons d’actualisation émis pour les applications tierces) | Les liens de partage protégés par mot de passe redemandent le mot de passe, les applications tierces doivent être autorisées à nouveau, et les applications ne peuvent pas accéder à Teable tant que leurs identifiants n’ont pas été actualisés |
| `BACKEND_SESSION_SECRET` | Vérifie les sessions de connexion existantes | Après une durée de vie de session (`BACKEND_SESSION_EXPIRES_IN`, 7 jours par défaut) | Tout le monde doit se reconnecter |
| `BACKEND_INVITATION_SECRET` | Vérifie les liens d’invitation déjà envoyés | Les invitations par e-mail expirent au bout d’un mois. Les liens d’invitation créés dans un Espace ou un Projet n’expirent jamais : une fois `_OLD` supprimé, ils sont toujours listés mais ne fonctionnent plus ; supprimez-les donc et créez-en de nouveaux | Les invitations par e-mail en attente et les liens d’invitation existants cessent de fonctionner ; invitez à nouveau ces personnes et créez de nouveaux liens |
| `BACKEND_MAIL_ENCRYPTION_KEY` / `IV` | Vérifie les liens de désabonnement des e-mails déjà envoyés | À vous de décider. Les liens de désabonnement n’expirent pas ; le supprimer rompt les liens des anciens e-mails | Les liens de désabonnement des anciens e-mails cessent de fonctionner |
| `BACKEND_ACCESS_TOKEN_ENCRYPTION_KEY` / `IV` | Maintient en fonctionnement les jetons d’accès personnels émis avec l’ancienne paire key/iv | Lorsque l’onglet [Jetons d'accès personnels](/fr/basic/admin-panel/key-rotation#personal-access-tokens) n’affiche aucun jeton qui dépend d’une clé plus ancienne | Ces jetons d’accès personnels cessent aussitôt de fonctionner et leurs propriétaires doivent les régénérer. Les chaînes de connexion des locataires de base de données stockées avec cette paire key/iv ne peuvent pas non plus être déchiffrées |
| `BACKEND_STORAGE_ENCRYPTION_KEY` / `IV` | Inutile | — | Les liens de pièces jointes du stockage local déjà émis cessent de fonctionner ; l’actualisation de la page en récupère de nouveaux |

Les automatisations actives s’exécutent à partir d’une copie de leurs étapes que le rechiffrement ne réécrit pas. Une automatisation qui conserve un mot de passe de messagerie ou un secret de webhook dans l’étape elle-même le lit toujours avec l’ancienne valeur. Avant de supprimer `BACKEND_THIRD_PARTY_CREDENTIAL_ENCRYPTION_SECRET_OLD` ou `BACKEND_STORED_CREDENTIAL_ENCRYPTION_SECRET_OLD`, modifiez chacune de ces automatisations et cliquez sur **Mettre à jour**, afin qu’elle s’exécute à partir des étapes rechiffrées. Cela n’a d’importance que si l’ancienne valeur était privée : avec une valeur publique, ces identifiants étaient stockés non chiffrés.

`BACKEND_DATA_DB_URL_ENCRYPTION_KEY` / `IV` portent l’étiquette **Obsolète** sur la page. Elles ne servent qu’aux chaînes de connexion des [locataires de base de données](/fr/basic/admin-panel/database-tenant) stockées dans l’ancien format. Terminez d’abord le rechiffrement ci-dessus, qui réécrit ces chaînes de connexion dans le format protégé par `SECRET_KEY`, puis supprimez les deux variables. Elles n’ont pas besoin de `_OLD`.

`BACKEND_ENV_VARIABLE_SECRET`, `BACKEND_AI_CONFIG_ENCRYPTION_SECRET`, `BACKEND_THIRD_PARTY_CREDENTIAL_ENCRYPTION_SECRET` et `BACKEND_DATA_DB_URL_ENCRYPTION_SECRET` portent elles aussi l’étiquette **Obsolète** sur la page : `BACKEND_STORED_CREDENTIAL_ENCRYPTION_SECRET` les remplace. Chacune reste prise en compte tant qu’elle est définie, et son `_OLD` fonctionne toujours. Ne les définissez pas sur un nouveau déploiement et supprimez celles que vous avez comme décrit ci-dessus : une version ultérieure pourrait ne plus les lire.

<Warning>Ne placez jamais une valeur publique ou ayant fuité dans `BACKEND_JWT_SECRET_OLD` ou `BACKEND_SESSION_SECRET_OLD`. Une valeur placée dans `_OLD` est toujours acceptée ; l’instance continuerait donc d’accepter des jetons et des sessions que n’importe qui peut fabriquer avec elle. Dans ce cas, basculez directement et laissez les utilisateurs se reconnecter.</Warning>

## Passer à votre propre SECRET_KEY {#own-secret-key}

Lorsque `SECRET_KEY` n’est pas défini, ou qu’il est encore la valeur par défaut publique, chaque secret qui le suit utilise une valeur publique. Mettre en place votre propre `SECRET_KEY` les change tous d’un coup ; les anciennes valeurs vont donc d’abord dans `_OLD` pour que les données existantes restent lisibles.

1. Générez le nouveau secret racine :

   ```bash
   openssl rand -base64 32
   ```

2. Préparez les variables `_OLD`. Choisissez la colonne qui correspond à l’état de départ de l’instance, et ignorez une ligne lorsque la page liste une variable dédiée pour ce secret, car sa valeur ne change pas avec `SECRET_KEY` :

   | Variable | `SECRET_KEY` n’a jamais été défini | `SECRET_KEY` était défini et est en cours de remplacement |
   |---|---|---|
   | `BACKEND_ENV_VARIABLE_SECRET_OLD` | `defaultSecretKey` | L’ancien `SECRET_KEY` |
   | `BACKEND_AI_CONFIG_ENCRYPTION_SECRET_OLD` | `defaultSecretKey` | L’ancien `SECRET_KEY` |
   | `BACKEND_THIRD_PARTY_CREDENTIAL_ENCRYPTION_SECRET_OLD` | Inutile : ces identifiants étaient stockés non chiffrés, et le rechiffrement les chiffre | L’ancien `SECRET_KEY` |
   | `BACKEND_INVITATION_SECRET_OLD` (facultatif, conserve les liens d’invitation déjà envoyés) | `defaultSecretKey` | L’ancien `SECRET_KEY` |
   | `BACKEND_ACCESS_TOKEN_ENCRYPTION_KEY_OLD` / `IV_OLD` (conserve les jetons d’accès personnels déjà émis) | Inutile : les anciennes valeurs intégrées restent automatiquement actives, pour le déchiffrement uniquement | Dérivé de l’ancien `SECRET_KEY`, voir l’exemple ci-dessous |
   | `BACKEND_MAIL_ENCRYPTION_KEY_OLD` / `IV_OLD` (facultatif, conserve les liens de désabonnement des e-mails déjà envoyés) | Inutile, comme ci-dessus | Dérivé de l’ancien `SECRET_KEY`, voir l’exemple ci-dessous |
   | `BACKEND_DATA_DB_URL_ENCRYPTION_SECRET_OLD` (si vous utilisez des locataires de base de données) | Inutile | L’ancien `SECRET_KEY` |
   | `BACKEND_DATA_DB_URL_ENCRYPTION_KEY_OLD` / `IV_OLD` (si vous utilisez des locataires de base de données et n’avez jamais défini cette paire) | `ed333d03ac334ea2` / `3c50b81e61cb7f52` | Dérivé de l’ancien `SECRET_KEY`, voir l’exemple ci-dessous |
   | `BACKEND_JWT_SECRET_OLD`, `BACKEND_SESSION_SECRET_OLD` | Ne pas définir : l’ancienne valeur est publique | Ne les définissez que si l’ancienne valeur n’est pas publique et n’a pas fuité |

   Les valeurs « Dérivé de l’ancien `SECRET_KEY` » de la dernière colonne sont les 16 premiers caractères hexadécimaux d’un SHA-256. Les [exemples Docker Compose](#docker-compose-examples) ci-dessous montrent comment les calculer.

   Au lieu des variables `_OLD` des trois premières lignes et de `BACKEND_DATA_DB_URL_ENCRYPTION_SECRET_OLD`, vous pouvez définir uniquement `BACKEND_STORED_CREDENTIAL_ENCRYPTION_SECRET_OLD` : `defaultSecretKey` si `SECRET_KEY` n’a jamais été défini, l’ancien `SECRET_KEY` sinon. Cette seule variable lit toutes ces données.

3. Arrêtez l’instance, définissez le nouveau `SECRET_KEY` et les variables `_OLD` ci-dessus, et assurez-vous que `SANDBOX_JWT_SECRET` est défini (le backend et le service sandbox partagent une même valeur). Démarrez ensuite tous les réplicas.
4. À partir de là, suivez les étapes 2 à 6 de [Supprimer les variables dédiées](#remove-dedicated-variables) : simulation, rechiffrement, actualisation des identifiants des applications, vérification par sondage, puis suppression de chaque `_OLD` le moment venu. Sans `BACKEND_JWT_SECRET_OLD`, les applications ne peuvent pas accéder à Teable tant que leurs identifiants n’ont pas été actualisés ; faites-le donc dans [JWT credentials](/fr/basic/admin-panel/jwt-credentials) dès que l’instance est démarrée.

### Exemples de `.env` pour Docker Compose {#docker-compose-examples}

Sur un déploiement Docker Compose, l’un des blocs ci-dessous écrit le nouveau `SECRET_KEY` et les variables `_OLD` des étapes 2 et 3 dans le fichier `.env` du répertoire de déploiement. Arrêtez d’abord l’instance et sauvegardez `.env`, puis, une fois le bloc exécuté, redémarrez-la avec `docker compose up -d`. Un bloc qui trouve `.env` dans un état inattendu, par exemple avec des variables `_OLD` déjà présentes, le signale et ne modifie rien. Les blocs écrivent tous les `_OLD` du tableau : si la page liste une variable dédiée pour l’un de ces secrets, supprimez la ligne `_OLD` de ce secret dans `.env` avant de démarrer l’instance. Pour toute autre configuration, ajoutez les mêmes variables à l’environnement de l’application Teable. Si vous avez déployé avec le [kit de déploiement complet](https://github.com/teableio/teable-deployment), les variables se trouvent ailleurs et sont générées différemment : suivez plutôt la section « App secrets » du README Docker ou Helm du kit.

### Après la bascule

Une fois le nouveau `SECRET_KEY` en place :

- Sans `BACKEND_JWT_SECRET_OLD` ni `BACKEND_SESSION_SECRET_OLD`, tout le monde doit se reconnecter, et les visiteurs doivent saisir à nouveau le mot de passe des liens de partage protégés par mot de passe.
- Sans `BACKEND_INVITATION_SECRET_OLD`, les invitations par e-mail en attente et les liens d’invitation existants cessent de fonctionner : invitez à nouveau ces personnes et créez de nouveaux liens.
- Avec le stockage local, les liens de pièces jointes copiés auparavant cessent de fonctionner. Les aperçus fonctionnent à nouveau une fois la page actualisée.
- Si vous avez utilisé la variante MinIO de la page [Déploiement Docker](/fr/deploy/docker) (`MINIO_SECRET_KEY=${SECRET_KEY}`), le mot de passe root de MinIO change en même temps que `SECRET_KEY`. Les fichiers et les buckets existants ne sont pas affectés ; les liens de pièces jointes émis auparavant cessent de fonctionner jusqu’à l’actualisation de la page.
- Les jetons d’accès personnels, les liens de désabonnement, les connexions des locataires de base de données, la configuration IA et les variables d’environnement des applications continuent de fonctionner.

Si la page liste des variables dédiées en plus de `SECRET_KEY`, traitez-les ensuite comme décrit dans [Supprimer les variables dédiées](#remove-dedicated-variables). Une variable qui a sa propre valeur ne change pas avec `SECRET_KEY` ; c’est pourquoi son `_OLD` est omis ci-dessus : vous aurez besoin de ce `_OLD` pour la valeur propre à cette variable lorsque vous la supprimerez.

## Facultatif : un secret racine distinct pour les identifiants stockés {#stored-credential-root}

`BACKEND_STORED_CREDENTIAL_ENCRYPTION_SECRET` donne aux identifiants chiffrés dans la base de données leur propre secret racine, à la place de `SECRET_KEY` : variables d’environnement des applications, configuration IA, identifiants tiers et chaînes de connexion des [locataires de base de données](/fr/basic/admin-panel/database-tenant). Une fois ces données placées sous ce secret, un changement de `SECRET_KEY` ne les affecte plus. La variable est facultative : `SECRET_KEY` seul suffit.

Elle remplace `BACKEND_ENV_VARIABLE_SECRET`, `BACKEND_AI_CONFIG_ENCRYPTION_SECRET`, `BACKEND_THIRD_PARTY_CREDENTIAL_ENCRYPTION_SECRET` et `BACKEND_DATA_DB_URL_ENCRYPTION_SECRET`, qui couvraient chacune un type de ces données et sont désormais obsolètes. Tant que l’une d’elles est encore définie, elle a la priorité pour son type de données. Supprimez-la comme décrit dans [Supprimer les variables dédiées](#remove-dedicated-variables) ; le rechiffrement place alors ses données sous le nouveau secret racine.

Pour l’activer, `SECRET_KEY` doit déjà être votre propre valeur :

1. Générez une valeur avec `openssl rand -base64 32`.
2. Arrêtez l’instance, définissez `BACKEND_STORED_CREDENTIAL_ENCRYPTION_SECRET`, puis démarrez tous les réplicas. Les données stockées sous `SECRET_KEY` restent lisibles sans aucun `_OLD` : `SECRET_KEY` continue de les déchiffrer.
3. Lancez la simulation et le rechiffrement comme aux étapes 2 et 3 de [Supprimer les variables dédiées](#remove-dedicated-variables).

Si vous ne pouvez pas arrêter tous les réplicas en même temps, définissez d’abord `BACKEND_STORED_CREDENTIAL_ENCRYPTION_SECRET_OLD` sur la nouvelle valeur pour chacun d’eux, et ne définissez la variable elle-même qu’une fois qu’ils ont tous redémarré. `_OLD` ne chiffre rien : il permet à chaque réplica de lire ce que les autres écrivent pendant la bascule, et vous pouvez le supprimer dès que la variable est définie partout.

Pour changer la valeur plus tard, placez la nouvelle valeur dans la variable et la valeur actuelle dans `BACKEND_STORED_CREDENTIAL_ENCRYPTION_SECRET_OLD`, puis rechiffrez. Ce seul `_OLD` lit tous les types de données énumérés ci-dessus.

## Retour arrière

- **Avant le rechiffrement** : remettez les variables d’environnement dans leur état antérieur et redémarrez. Ce qui a été enregistré entre-temps (identifiants, clés IA, variables d’application, nouveaux jetons et nouvelles sessions) a été écrit avec la nouvelle configuration et ne peut pas être lu avec l’ancienne ; ces éléments redeviennent lisibles dès que vous repassez à la nouvelle configuration.
- **Après le rechiffrement** : ne rétablissez pas les anciennes variables d’environnement et ne passez pas à une image plus ancienne. Les données réécrites ne s’ouvrent qu’avec la clé actuelle. Si vous devez vraiment revenir en arrière, restaurez la base de données et les variables d’environnement à partir de la sauvegarde effectuée avant la modification.

## FAQ

<AccordionGroup>
  <Accordion title="Comment confirmer qu’une variable suit SECRET_KEY après sa suppression ?">
    Consultez à nouveau l’onglet **Secrets du serveur** après le redémarrage. Le nombre de variables dédiées affiché en haut a diminué. Si la variable a un `_OLD` défini, sa ligne reste jusqu’à la suppression de celui-ci, et **Valeur issue de** indique désormais **Se rabat sur SECRET_KEY** ou **Dérivé de SECRET_KEY** ; sinon, la ligne a disparu.
  </Accordion>
  <Accordion title="Que faire si la simulation affiche des lignes indéchiffrables ?">
    Ni la clé actuelle ni aucun `_OLD` configuré n’ouvre ces lignes ; le rechiffrement les ignore donc et les laisse telles quelles. Le plus souvent, une ancienne valeur manque : à l’aide du nom de table et des ID de lignes fournis par la page, placez la valeur avec laquelle ces lignes ont été chiffrées dans la variable `_OLD` correspondante, redémarrez, puis relancez la simulation.
  </Accordion>
  <Accordion title="Je veux conserver une variable dédiée et seulement changer sa valeur. Comment faire ?">
    Placez la nouvelle valeur dans la variable et déplacez la valeur actuelle dans la variable de même nom suivie de `_OLD`. Changez une clé et son iv ensemble et définissez les deux variables `_OLD` : le serveur refuse de démarrer avec une seule. Générez ces valeurs de 16 caractères avec `openssl rand -hex 8` et toutes les autres avec `openssl rand -base64 32`. Si une valeur a fuité, ne la placez pas dans `_OLD` ; remplacez-la directement.
  </Accordion>
  <Accordion title="Que faire si l’instance ne dispose pas de la page Rotation des clés ?">
    L’édition Community et les forfaits inférieurs à Business n’en disposent pas. Un nouveau déploiement n’est pas concerné. Lorsqu’une instance existante change un secret, conservez l’ancienne valeur dans la variable `_OLD` correspondante et les données existantes restent lisibles. Sans le rechiffrement, les données stockées restent sous l’ancienne valeur jusqu’à ce qu’elles soient enregistrées à nouveau ; laissez donc en place les variables `_OLD` des données stockées. Les applications créées avec App Builder sont le seul point à traiter à la main : lorsque le secret de signature JWT change sans `BACKEND_JWT_SECRET_OLD`, renouvelez les identifiants de chaque application depuis l’application elle-même, comme décrit sous [Jeton d’accès Teable](/fr/basic/ai/app-builder#teable-access-token).
  </Accordion>
</AccordionGroup>
