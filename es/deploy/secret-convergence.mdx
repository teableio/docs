<Tip>La página de administración que se usa aquí está disponible para el plan Business autoalojado y los planes superiores</Tip>

`SECRET_KEY` puede proporcionar todos los secretos del servidor que Teable necesita. Los JWT, las sesiones y las distintas claves de cifrado la usan directamente, o usan una clave derivada de ella, siempre que no tengan una variable propia. La aplicación necesita dos secretos propios:

- `SECRET_KEY`: el secreto raíz.
- `SANDBOX_JWT_SECRET`: firma los tokens de ejecución del entorno aislado. El entorno aislado ejecuta los scripts de tus usuarios y nunca tiene el secreto raíz, por lo que este secreto no sigue a `SECRET_KEY`.

Ya no se recomienda establecer las demás variables dedicadas (`BACKEND_JWT_SECRET`, `BACKEND_SESSION_SECRET`, las `*_ENCRYPTION_*`, etc.), y una versión posterior podría dejar de leer la mayoría de ellas. Esta página explica cómo pasar una instancia existente a estos dos secretos sin perder los datos que ya contiene.

Una variable opcional es la excepción: `BACKEND_STORED_CREDENTIAL_ENCRYPTION_SECRET` da a las credenciales cifradas en la base de datos un secreto raíz propio. Consulta [Un secreto raíz propio para las credenciales almacenadas](#stored-credential-root).

Un despliegue nuevo no necesita nada de esto: genera los dos secretos como se describe en [Variables de entorno](/es/deploy/env#secrets-and-rotation) y deja el resto sin establecer.

<Warning>Una versión posterior se negará a arrancar mientras `SECRET_KEY` no esté establecida o siga siendo el valor predeterminado público. Si tu instancia funciona así, [cambia a tu propia SECRET_KEY](#own-secret-key) antes de actualizar a esa versión.</Warning>

## Antes de empezar

- **Actualiza primero.** Lleva la instancia a la versión más reciente antes de empezar. Los pasos usan la página **Rotación de claves** de Administración del sistema; si Administración del sistema no la muestra, la versión es demasiado antigua o el plan es inferior a Business.
- **Haz una copia de seguridad.** Haz una copia de seguridad de la base de datos y de todas las variables de entorno. Después de un recifrado, los datos solo se abren con la clave actual.
- **Planifica una ventana de mantenimiento.** La instancia se reinicia durante el proceso, y los usuarios vuelven a iniciar sesión cuando cambia el secreto de sesión.
- **Cambia todas las réplicas a la vez.** Todas las réplicas y los workers deben reiniciarse con la misma configuración nueva antes de que vuelvas a cifrar. Una réplica que siga con la configuración anterior no puede leer los datos reescritos.

## Paso 1: comprueba qué está establecido

Mientras una instancia siga funcionando con los valores predeterminados integrados públicos, el registro de inicio enumera los secretos que faltan, y los administradores de la instancia ven un elemento **Secretos del servidor** en **Administración del sistema → Configuración de instancia**, dentro del panel **Configuración pendiente**. El registro de inicio también muestra un bloque de variables que fija los valores actuales. Esta guía no lo necesita; en una instancia que ya haya añadido el bloque, esas variables aparecen en la página como variables dedicadas marcadas con **Valor público**.

Para ver la situación completa, abre **Administración del sistema → Rotación de claves → Secretos del servidor** como administrador de la instancia. Enumera `SECRET_KEY`, `SANDBOX_JWT_SECRET` y cada secreto que todavía tiene establecida su propia variable o una variable `_OLD`. Un secreto que no aparece en la lista sigue a `SECRET_KEY` y no necesita nada. [Rotación de claves](/es/basic/admin-panel/key-rotation#server-secrets) explica las columnas.

Usa lo que muestra la página para saber qué casos se aplican; puede haber más de uno:

| La página muestra | Qué significa | Siguiente paso |
|---|---|---|
| Solo las filas `SECRET_KEY` y `SANDBOX_JWT_SECRET`, ninguna marcada con **Valor público** | Ya es el estado objetivo | No hay que hacer nada |
| `SECRET_KEY` sin **Valor público**, además de variables dedicadas | El secreto raíz está bien; quedan variables dedicadas | [Eliminar las variables dedicadas](#remove-dedicated-variables) |
| `SECRET_KEY` aparece como no establecida, o marcada con **Valor público** | La instancia funciona con valores predeterminados integrados públicos | [Cambiar a tu propia SECRET_KEY](#own-secret-key) |
| `SANDBOX_JWT_SECRET` marcada con **Valor público** | El secreto del entorno aislado sigue siendo el valor predeterminado público | Genera un valor con `openssl rand -base64 32`, establécelo para la aplicación y, si ejecutas un servicio de entorno aislado, también para ese servicio, y después reinicia. Ningún dato almacenado depende de él |
| Filas que aparecen solo por sus variables `_OLD` | Todavía se conservan valores anteriores | Elimina cada una cuando [la tabla siguiente](#old-value-retention) lo permita |

<Warning>Un valor copiado de la documentación o de un archivo de ejemplo es tan público como un valor predeterminado integrado, pero la página no puede detectarlo. La plantilla de la página [Despliegue con Docker](/es/deploy/docker) contiene `SECRET_KEY=replace_this_secret_key`: si la instancia sigue funcionando con ese valor, considera `SECRET_KEY` pública y sigue [Cambiar a tu propia SECRET_KEY](#own-secret-key).</Warning>

## Eliminar las variables dedicadas {#remove-dedicated-variables}

Para cada fila cuyo **Valor de** indique **Variable propia**, salvo las de las propias `SECRET_KEY` y `SANDBOX_JWT_SECRET`, mira la última columna, **Igual que solo con SECRET_KEY**:

- **Igual**: elimina la variable. El valor no cambia y ningún dato se ve afectado.
- **Distinto**: mueve su valor actual a la variable del mismo nombre con `_OLD` añadido al final (por ejemplo, `BACKEND_AI_CONFIG_ENCRYPTION_SECRET_OLD`) y después elimina la propia variable. `_OLD` solo verifica o descifra datos existentes; todo lo nuevo usa `SECRET_KEY`. Para un par de clave e iv, establece las dos variables `_OLD` a la vez. Una variable que [la tabla siguiente](#old-value-retention) no incluye no tiene `_OLD`: elimínala sin más, salvo que la página la etiquete como **Obsoleto** (consulta la nota situada debajo de la tabla).

Cada variable `_OLD` guarda un único valor anterior. Si el entorno ya tiene variables `_OLD`, por ejemplo de un cambio previo, termina el recifrado y elimínalas antes de empezar otra ronda. De lo contrario, los datos que sigan cifrados con el valor más antiguo dejarán de poder leerse y habrá que volver a introducirlos.

Puedes tratar todas las variables en un solo cambio:

1. Detén la instancia, edita las variables de entorno como se describe arriba y después inicia todas las réplicas.
2. Abre la pestaña [Textos cifrados almacenados](/es/basic/admin-panel/key-rotation#stored-ciphertexts) y haz clic en **Dry-run** (simulación). La columna **No descifrables** debe ser 0 en todas partes. Si no lo es, falta un valor `_OLD`: añádelo antes de continuar.
3. Haz clic en **Volver a cifrar** y después ejecuta la simulación una vez más. Cuando **Necesitan recifrado** y **No descifrables** sean ambos 0, todo el texto cifrado almacenado estará bajo `SECRET_KEY`.
4. Si el secreto de firma de JWT ha cambiado y la instancia tiene aplicaciones de App Builder, abre [Credenciales JWT](/es/basic/admin-panel/jwt-credentials) y renueva las credenciales de todas las aplicaciones de **Requieren atención**.
5. Comprueba por muestreo el inicio de sesión, una llamada con un token de acceso personal, las funciones de IA, las credenciales de terceros de las automatizaciones y las aplicaciones publicadas.
6. Elimina cada variable `_OLD` cuando la tabla siguiente lo permita y reinicia después de cada eliminación.

### Cuánto tiempo se conserva cada valor anterior {#old-value-retention}

| Variable | Qué hace `_OLD` | Cuándo puedes eliminar `_OLD` | Cambiar sin `_OLD` |
|---|---|---|---|
| `BACKEND_ENV_VARIABLE_SECRET`, `BACKEND_AI_CONFIG_ENCRYPTION_SECRET`, `BACKEND_THIRD_PARTY_CREDENTIAL_ENCRYPTION_SECRET` | Descifra las variables de entorno de las aplicaciones, las claves de proveedores de IA y las credenciales de terceros almacenadas con el valor anterior | Después del recifrado, una vez que las dos columnas de la simulación sean 0. Para el secreto de las credenciales de terceros, consulta la nota sobre las automatizaciones situada debajo de la tabla | Esos datos no se pueden descifrar. Establécelo siempre |
| `BACKEND_STORED_CREDENTIAL_ENCRYPTION_SECRET` | Descifra todo lo que cubre la variable y que se almacenó con el valor anterior: variables de entorno de las aplicaciones, claves de proveedores de IA, credenciales de terceros y cadenas de conexión de inquilinos de base de datos | Después del recifrado, una vez que las dos columnas de la simulación sean 0. La nota sobre las automatizaciones que hay bajo la tabla también se aplica aquí | Esos datos no se pueden descifrar. Establécelo siempre |
| `BACKEND_DATA_DB_URL_ENCRYPTION_SECRET` | Descifra las cadenas de conexión de los [inquilinos de base de datos](/es/basic/admin-panel/database-tenant) almacenadas con el valor anterior | Después del recifrado, una vez que las dos columnas de la simulación sean 0 | Esos datos no se pueden descifrar. Establécelo siempre |
| `BACKEND_DATA_DB_URL_ENCRYPTION_KEY` / `IV` | Descifran las cadenas de conexión de los [inquilinos de base de datos](/es/basic/admin-panel/database-tenant) almacenadas con el valor anterior | Después del recifrado, una vez que las dos columnas de la simulación sean 0 | Esas cadenas de conexión no se pueden descifrar. Establécelas siempre |
| `BACKEND_JWT_SECRET` | Verifica los tokens firmados con el secreto anterior | Cuando **Requieren atención**, **Error de actualización** y **Credenciales publicadas desactualizadas** estén todas vacías en [Credenciales JWT](/es/basic/admin-panel/jwt-credentials) y hayan pasado 30 días (la vigencia de los tokens de actualización emitidos a aplicaciones de terceros) | Los enlaces compartidos protegidos con contraseña vuelven a pedir la contraseña, las aplicaciones de terceros deben autorizarse de nuevo y las aplicaciones no pueden acceder a Teable hasta que se renueven sus credenciales |
| `BACKEND_SESSION_SECRET` | Verifica las sesiones de inicio de sesión existentes | Cuando haya transcurrido la vigencia de una sesión (`BACKEND_SESSION_EXPIRES_IN`, 7 días de forma predeterminada) | Todos vuelven a iniciar sesión |
| `BACKEND_INVITATION_SECRET` | Verifica los enlaces de invitación ya enviados | Las invitaciones por correo electrónico caducan al cabo de un mes. Los enlaces de invitación creados en un Espacio o un Proyecto no caducan nunca: una vez eliminado `_OLD`, siguen apareciendo en la lista pero ya no funcionan, así que elimínalos y crea otros nuevos | Las invitaciones por correo electrónico pendientes y los enlaces de invitación existentes dejan de funcionar; vuelve a invitar a esas personas y crea enlaces nuevos |
| `BACKEND_MAIL_ENCRYPTION_KEY` / `IV` | Verifica los enlaces para darse de baja de los correos ya enviados | Tú decides. Los enlaces para darse de baja no caducan; al eliminarlo, los enlaces de los correos antiguos dejan de funcionar | Los enlaces para darse de baja de los correos antiguos dejan de funcionar |
| `BACKEND_ACCESS_TOKEN_ENCRYPTION_KEY` / `IV` | Mantiene en funcionamiento los tokens de acceso personal emitidos con el key/iv anterior | Cuando la pestaña [Tokens de acceso personal](/es/basic/admin-panel/key-rotation#personal-access-tokens) no muestre ningún token que dependa de una clave anterior | Esos tokens de acceso personal dejan de funcionar de inmediato y sus propietarios tienen que regenerarlos. Las cadenas de conexión de inquilinos de base de datos almacenadas con este key/iv tampoco se pueden descifrar |
| `BACKEND_STORAGE_ENCRYPTION_KEY` / `IV` | No es necesario | — | Los enlaces de adjuntos del almacenamiento local ya emitidos dejan de funcionar; al actualizar la página se obtienen otros nuevos |

Las automatizaciones activas se ejecutan a partir de una copia de sus pasos que el recifrado no reescribe. Una automatización que guarda una contraseña de correo o un secreto de webhook en el propio paso lo sigue leyendo con el valor anterior. Antes de eliminar `BACKEND_THIRD_PARTY_CREDENTIAL_ENCRYPTION_SECRET_OLD` o `BACKEND_STORED_CREDENTIAL_ENCRYPTION_SECRET_OLD`, edita cada una de esas automatizaciones y haz clic en **Actualizar**, para que se ejecute a partir de los pasos recifrados. Esto solo importa cuando el valor anterior era privado: con un valor público, estas credenciales se almacenaban sin cifrar.

`BACKEND_DATA_DB_URL_ENCRYPTION_KEY` / `IV` llevan la etiqueta **Obsoleto** en la página. Solo sirven para las cadenas de conexión de [inquilinos de base de datos](/es/basic/admin-panel/database-tenant) almacenadas en el formato antiguo. Termina primero el recifrado descrito arriba, que reescribe esas cadenas de conexión en el formato protegido por `SECRET_KEY`, y después elimina las dos variables. No necesitan `_OLD`.

`BACKEND_ENV_VARIABLE_SECRET`, `BACKEND_AI_CONFIG_ENCRYPTION_SECRET`, `BACKEND_THIRD_PARTY_CREDENTIAL_ENCRYPTION_SECRET` y `BACKEND_DATA_DB_URL_ENCRYPTION_SECRET` también llevan la etiqueta **Obsoleto** en la página: `BACKEND_STORED_CREDENTIAL_ENCRYPTION_SECRET` las sustituye. Cada una sigue teniendo efecto mientras esté establecida, y su `_OLD` sigue funcionando. No las establezcas en un despliegue nuevo y elimina las que tengas como se describe arriba: una versión posterior puede dejar de leerlas.

<Warning>Nunca pongas un valor público o filtrado en `BACKEND_JWT_SECRET_OLD` ni en `BACKEND_SESSION_SECRET_OLD`. Un valor en `_OLD` se sigue aceptando, por lo que la instancia seguiría aceptando tokens y sesiones que cualquiera puede falsificar con él. En ese caso, cambia directamente y deja que los usuarios vuelvan a iniciar sesión.</Warning>

## Cambiar a tu propia SECRET_KEY {#own-secret-key}

Cuando `SECRET_KEY` no está establecida, o sigue siendo el valor predeterminado público, todos los secretos que la siguen usan un valor público. Al poner tu propia `SECRET_KEY`, todos ellos cambian a la vez, así que los valores anteriores se guardan primero en `_OLD` para que los datos existentes sigan siendo legibles.

1. Genera el nuevo secreto raíz:

   ```bash
   openssl rand -base64 32
   ```

2. Prepara las variables `_OLD`. Elige la columna que corresponda al punto de partida de la instancia y omite una fila cuando la página muestre una variable dedicada para ese secreto, porque su valor no cambia con `SECRET_KEY`:

   | Variable | `SECRET_KEY` nunca se estableció | `SECRET_KEY` estaba establecida y se va a sustituir |
   |---|---|---|
   | `BACKEND_ENV_VARIABLE_SECRET_OLD` | `defaultSecretKey` | La `SECRET_KEY` anterior |
   | `BACKEND_AI_CONFIG_ENCRYPTION_SECRET_OLD` | `defaultSecretKey` | La `SECRET_KEY` anterior |
   | `BACKEND_THIRD_PARTY_CREDENTIAL_ENCRYPTION_SECRET_OLD` | No es necesario: esas credenciales se almacenaban sin cifrar, y el recifrado las cifra | La `SECRET_KEY` anterior |
   | `BACKEND_INVITATION_SECRET_OLD` (opcional, conserva los enlaces de invitación ya enviados) | `defaultSecretKey` | La `SECRET_KEY` anterior |
   | `BACKEND_ACCESS_TOKEN_ENCRYPTION_KEY_OLD` / `IV_OLD` (conserva los tokens de acceso personal ya emitidos) | No es necesario: los valores anteriores integrados se mantienen automáticamente, solo para descifrar | Derivados de la `SECRET_KEY` anterior; consulta el ejemplo siguiente |
   | `BACKEND_MAIL_ENCRYPTION_KEY_OLD` / `IV_OLD` (opcional, conserva los enlaces para darse de baja de los correos ya enviados) | No es necesario, igual que arriba | Derivados de la `SECRET_KEY` anterior; consulta el ejemplo siguiente |
   | `BACKEND_DATA_DB_URL_ENCRYPTION_SECRET_OLD` (si usas inquilinos de base de datos) | No es necesario | La `SECRET_KEY` anterior |
   | `BACKEND_DATA_DB_URL_ENCRYPTION_KEY_OLD` / `IV_OLD` (si usas inquilinos de base de datos y nunca estableciste este par) | `ed333d03ac334ea2` / `3c50b81e61cb7f52` | Derivados de la `SECRET_KEY` anterior; consulta el ejemplo siguiente |
   | `BACKEND_JWT_SECRET_OLD`, `BACKEND_SESSION_SECRET_OLD` | Déjalas sin establecer: el valor anterior es público | Establécelas solo si el valor anterior no es público ni se ha filtrado |

   Los valores «derivados de la `SECRET_KEY` anterior» de la última columna son los primeros 16 caracteres hexadecimales de un SHA-256. Los [ejemplos de Docker Compose](#docker-compose-examples) siguientes muestran cómo calcularlos.

   En lugar de las variables `_OLD` de las tres primeras filas y de `BACKEND_DATA_DB_URL_ENCRYPTION_SECRET_OLD`, puedes establecer solo `BACKEND_STORED_CREDENTIAL_ENCRYPTION_SECRET_OLD`: con `defaultSecretKey` si `SECRET_KEY` nunca se estableció, y con la `SECRET_KEY` anterior en caso contrario. Esa única variable lee todos esos datos.

3. Detén la instancia, establece la nueva `SECRET_KEY` y las variables `_OLD` indicadas arriba, y asegúrate de que `SANDBOX_JWT_SECRET` esté establecida (el backend y el servicio del entorno aislado comparten un mismo valor). Después inicia todas las réplicas.
4. A partir de aquí, sigue los pasos 2 a 6 de [Eliminar las variables dedicadas](#remove-dedicated-variables): simulación, recifrado, renovación de las credenciales de las aplicaciones, comprobación por muestreo y eliminación de cada `_OLD` cuando llegue su momento. Sin `BACKEND_JWT_SECRET_OLD`, las aplicaciones no pueden acceder a Teable hasta que se renueven sus credenciales, así que hazlo en [Credenciales JWT](/es/basic/admin-panel/jwt-credentials) justo después de que la instancia esté en marcha.

### Ejemplos de `.env` para Docker Compose {#docker-compose-examples}

En un despliegue con Docker Compose, uno de los bloques siguientes escribe la nueva `SECRET_KEY` y las variables `_OLD` de los pasos 2 y 3 en el archivo `.env` del directorio de despliegue. Antes, detén la instancia y haz una copia de seguridad de `.env`; después, vuelve a iniciarla con `docker compose up -d`. Un bloque que encuentra `.env` en un estado que no espera, por ejemplo con variables `_OLD` ya presentes, lo indica y no cambia nada. Los bloques escriben todos los `_OLD` de la tabla: si la página muestra una variable dedicada para uno de esos secretos, elimina de `.env` la línea `_OLD` de ese secreto antes de iniciar la instancia. Para cualquier otra configuración, añade las mismas variables al entorno de la aplicación Teable. Si desplegaste con el [kit de despliegue con todas las funciones](https://github.com/teableio/teable-deployment), las variables están en otro lugar y se generan de otra forma: sigue en su lugar la sección «App secrets» del README de Docker o de Helm del kit.

### Después del cambio

Una vez que la nueva `SECRET_KEY` esté en uso:

- Sin `BACKEND_JWT_SECRET_OLD` ni `BACKEND_SESSION_SECRET_OLD`, todos vuelven a iniciar sesión, y los visitantes vuelven a introducir la contraseña de los enlaces compartidos protegidos con contraseña.
- Sin `BACKEND_INVITATION_SECRET_OLD`, las invitaciones por correo electrónico pendientes y los enlaces de invitación existentes dejan de funcionar: vuelve a invitar a esas personas y crea enlaces nuevos.
- Con almacenamiento local, los enlaces de adjuntos copiados anteriormente dejan de funcionar. Las vistas previas vuelven a funcionar en cuanto se actualiza la página.
- Si usaste la variante con MinIO de la página [Despliegue con Docker](/es/deploy/docker) (`MINIO_SECRET_KEY=${SECRET_KEY}`), la contraseña raíz de MinIO cambia junto con `SECRET_KEY`. Los archivos y buckets existentes no se ven afectados; los enlaces de adjuntos emitidos anteriormente dejan de funcionar hasta que se actualiza la página.
- Los tokens de acceso personal, los enlaces para darse de baja, las conexiones de los inquilinos de base de datos, la configuración de IA y las variables de entorno de las aplicaciones siguen funcionando.

Si la página muestra variables dedicadas además de `SECRET_KEY`, ocúpate de ellas después como se describe en [Eliminar las variables dedicadas](#remove-dedicated-variables). Una variable con un valor propio no cambia con `SECRET_KEY`, y por eso su `_OLD` se omite arriba: necesitarás ese `_OLD` para el valor propio de la variable cuando la elimines.

## Opcional: un secreto raíz propio para las credenciales almacenadas {#stored-credential-root}

`BACKEND_STORED_CREDENTIAL_ENCRYPTION_SECRET` da a las credenciales cifradas en la base de datos un secreto raíz propio, en lugar de `SECRET_KEY`: variables de entorno de las aplicaciones, configuración de IA, credenciales de terceros y cadenas de conexión de [inquilinos de base de datos](/es/basic/admin-panel/database-tenant). Una vez que esos datos están bajo ese secreto, cambiar `SECRET_KEY` ya no les afecta. La variable es opcional: basta con `SECRET_KEY`.

Sustituye a `BACKEND_ENV_VARIABLE_SECRET`, `BACKEND_AI_CONFIG_ENCRYPTION_SECRET`, `BACKEND_THIRD_PARTY_CREDENTIAL_ENCRYPTION_SECRET` y `BACKEND_DATA_DB_URL_ENCRYPTION_SECRET`, que cubrían cada una un tipo de esos datos y ahora están obsoletas. Mientras alguna de ellas siga establecida, tiene prioridad para su tipo de datos. Elimínala como se describe en [Eliminar las variables dedicadas](#remove-dedicated-variables); el recifrado pasa entonces sus datos al nuevo secreto raíz.

Para activarla, `SECRET_KEY` ya debe ser un valor propio:

1. Genera un valor con `openssl rand -base64 32`.
2. Detén la instancia, establece `BACKEND_STORED_CREDENTIAL_ENCRYPTION_SECRET` y después inicia todas las réplicas. Los datos almacenados bajo `SECRET_KEY` siguen siendo legibles sin ningún `_OLD`: `SECRET_KEY` los sigue descifrando.
3. Ejecuta la simulación y el recifrado como en los pasos 2 y 3 de [Eliminar las variables dedicadas](#remove-dedicated-variables).

Si no puedes detener todas las réplicas a la vez, establece primero `BACKEND_STORED_CREDENTIAL_ENCRYPTION_SECRET_OLD` con el nuevo valor en todas ellas, y establece la variable en sí solo cuando todas se hayan reiniciado. `_OLD` no cifra nada: permite que cada réplica lea lo que escriben las demás durante el cambio, y puedes eliminarla cuando la variable esté establecida en todas partes.

Para cambiar el valor más adelante, pon el nuevo valor en la variable y el actual en `BACKEND_STORED_CREDENTIAL_ENCRYPTION_SECRET_OLD`, y después vuelve a cifrar. Ese único `_OLD` lee todos los tipos de datos indicados arriba.

## Reversión

- **Antes del recifrado**: vuelve a dejar las variables de entorno como estaban y reinicia. Lo que se haya guardado entretanto (credenciales, claves de IA, variables de aplicaciones, tokens y sesiones nuevos) se escribió con la configuración nueva y no se puede leer con la anterior; vuelve a ser legible cuando cambies de nuevo a la configuración nueva.
- **Después del recifrado**: no reviertas las variables de entorno ni pases a una imagen anterior. Los datos reescritos solo se abren con la clave actual. Si de verdad tienes que volver atrás, restaura la base de datos y las variables de entorno desde la copia de seguridad realizada antes del cambio.

## Preguntas frecuentes

<AccordionGroup>
  <Accordion title="¿Cómo confirmo que una variable sigue a SECRET_KEY después de eliminarla?">
    Vuelve a mirar la pestaña **Secretos del servidor** después del reinicio. El recuento de variables dedicadas de la parte superior habrá disminuido. Si la variable tiene un `_OLD` establecido, su fila se mantiene hasta que este se elimine, y **Valor de** indica ahora **Recurre a SECRET_KEY** o **Derivado de SECRET_KEY**; de lo contrario, la fila desaparece.
  </Accordion>
  <Accordion title="¿Qué hago si la simulación muestra filas no descifrables?">
    Ni la clave actual ni ningún `_OLD` configurado abre esas filas, por lo que el recifrado las omite y las deja como están. Normalmente falta un valor anterior: usa el nombre de la tabla y los ID de fila que indica la página, pon el valor con el que se cifraron esas filas en la variable `_OLD` correspondiente, reinicia y vuelve a ejecutar la simulación.
  </Accordion>
  <Accordion title="Quiero conservar una variable dedicada y cambiar solo su valor. ¿Cómo lo hago?">
    Pon el valor nuevo en la variable y mueve el actual a la variable del mismo nombre con `_OLD` añadido al final. Cambia una clave y su iv a la vez y establece las dos variables `_OLD`: el servidor se niega a iniciarse con solo una. Genera estos valores de 16 caracteres con `openssl rand -hex 8` y todo lo demás con `openssl rand -base64 32`. Si un valor se ha filtrado, no lo pongas en `_OLD`; sustitúyelo directamente.
  </Accordion>
  <Accordion title="¿Qué ocurre si la instancia no tiene la página Rotación de claves?">
    La edición Community y los planes inferiores a Business no la tienen. Un despliegue nuevo no se ve afectado. Cuando una instancia existente cambie un secreto, conserva el valor anterior en la variable `_OLD` correspondiente y los datos existentes seguirán siendo legibles. Sin el recifrado, los datos almacenados permanecen bajo el valor anterior hasta que se vuelven a guardar, así que deja establecidas las variables `_OLD` de los datos almacenados. Las aplicaciones creadas con App Builder son lo único que hay que hacer a mano: cuando el secreto de firma de JWT cambia sin `BACKEND_JWT_SECRET_OLD`, rota las credenciales de cada aplicación desde la propia aplicación, como se describe en [Token de acceso de Teable](/es/basic/ai/app-builder#teable-access-token).
  </Accordion>
</AccordionGroup>
