<Tip>セルフホストのBusinessプラン以上で利用できます</Tip>

パス：システム管理 → キーのローテーション → JWT credentials（JWT認証情報）

[App Builder](/ja/basic/ai/app-builder)で作成したアプリは、有効期間の長い認証情報を2つ保持しています。アプリに保存されるTeableアクセストークンと、デプロイ時にランタイムへ書き込まれるAIアクセスキーです。どちらも、JWT署名シークレット（`BACKEND_JWT_SECRET`、未設定の場合は`SECRET_KEY`）で署名されています。このシークレットが変わると、アプリが引き続きTeableへアクセスするには、新しい認証情報が必要になります。このページでは、その作業を一括で行います。

## 使用する場面

- JWT署名シークレットが変わった場合。`BACKEND_JWT_SECRET`を削除して`SECRET_KEY`に従うようにした場合や、`SECRET_KEY`自体を変更した場合も含みます。手順の順序については、[シークレットの収束](/ja/deploy/secret-convergence)をご覧ください。
- アプリのデプロイ環境にある変数が漏えいした可能性があり、そのアプリのAIアクセスキーを無効にする必要がある場合。

## 各アプリの状態を確認する

一覧には、アプリごとに、Teableトークンが現在のシークレットと古いシークレットのどちらで署名されたか、公開状態、最後にデプロイされた日時、AIキーの有効期限が表示されます。一覧の上にあるボタンで絞り込めます。

| フィルター | 含まれるアプリ |
|---|---|
| Needs attention（要対応） | Teableトークンが現在のシークレットで署名されていないアプリ |
| Live credentials outdated（稼働中の認証情報が古い） | 認証情報は置き換えられたものの、再デプロイされていないアプリ。稼働中のアプリは、すでに使えなくなった古い認証情報を使い続けています |
| Refresh failed（更新失敗） | 前回の更新が成功しなかったアプリ |
| Published（公開済み） / Unpublished changes（未公開の変更あり） / All（すべて） | 公開状態による分類 |

## シークレットの変更後に認証情報を更新する

1. シークレットを変更するときに、古い値を`BACKEND_JWT_SECRET_OLD`に設定します。こうすると、更新が完了するまで、既存のトークンは有効なままです。古い値が公開されている場合や漏えいした場合は、設定しないでください。`_OLD`の値は引き続き受け付けられるため、その値で偽造されたトークンが使えるままになります。設定しない場合、アプリは更新されるまでTeableにアクセスできないため、再起動後すぐに更新してください。
2. **Needs attention**ですべてのアプリを選択し、**Refresh app credentials**（アプリの認証情報を更新）をクリックして、**Teable access token**（Teableアクセストークン）だけにチェックを入れます。
3. キューの処理が終わるまで待ちます。公開済みのアプリは、順番が来ると新しいトークンが発行されて再デプロイされ、その過程で、稼働中のAIキーも新しいシークレットで署名されます。未公開のアプリには新しいトークンが発行され、実行中のプレビューにはその場で反映されます。
4. `BACKEND_JWT_SECRET_OLD`を削除するのは、**Needs attention**、**Refresh failed**、**Live credentials outdated**がすべて空になってからにしてください。後の2つにあるアプリには、**Refresh app envs**（アプリの環境を更新）を使用します。

Teableは、各アプリのトークンを、JWT署名シークレットから派生したキーで暗号化して保存しています。古い値がなくなると、まだ更新されていないアプリは動作しなくなります。そのアプリのトークンを更新すれば、復旧します。

更新中は、次のようになります。

- 公開済みの各アプリは1回だけ再デプロイされ、リクエストが失敗するのは、そのアプリ自身の再デプロイが実行されている間だけです。
- 未公開の変更があるアプリでは、公開済みのバージョンが再デプロイされ、未公開の変更はそのまま残ります。
- ログインを有効にしているアプリでは、訪問者がログアウトされます。アプリのセッションがこのトークンで署名されているためです。

デプロイ環境にある変数が漏えいした可能性がある場合は、**AI access key**（AIアクセスキー）にもチェックを入れます。古いキーは直ちに使えなくなります。オーナーのローカルの`.env`や、ダウンロードしたコードにあるコピーも同様です。

## 再デプロイを分散させる

デプロイプロバイダーは通常、1つのアカウントが開始できるデプロイの数を制限しています。**Spread out the redeploys**（再デプロイを分散させる）にチェックを入れると、再デプロイは時間枠ごとにバッチで開始され、各時間枠で開始される数は、設定した数が上限になります。ページには、最後のバッチが開始されるおおよその時刻が表示されます。

デフォルトでは、各サーバーは公開済みのアプリを一度に1つずつ再デプロイします。アプリが多い場合は、環境変数`APP_ENV_REFRESH_CONCURRENCY`（デフォルトは`1`）を設定すると速くなります。ただし、その数のビルドが各サーバーで同時に実行されることになります。

## 稼働中の環境が更新されていないアプリに対応する

**Live credentials outdated**にあるアプリには、2つの対応方法があります。

- **Refresh app envs**は、公開済みアプリの稼働中のランタイムを、現在のTeableトークンと新しく署名されたAIキーを使って、その場で再構築します。新しいバージョンは作成されず、アプリのオーナーにも影響しません。
- **Check with deploy provider**（デプロイプロバイダーに確認）は、プロバイダー側ですでに再デプロイしたアプリのためのものです。稼働中のデプロイがビルドされた日時と、認証情報の変数が最後に更新された日時を読み取り、新しい認証情報が稼働中の環境に反映されていると確認できたアプリを、このフィルターから外します。読み取りを行うだけで、再デプロイは一切行われず、変数の値も読み取られません。現在は、Vercelにデプロイされたアプリだけに対応しています。
