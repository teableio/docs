<Tip>Available for self-hosted Business plan and above</Tip>

Path: System Admin → Table operations → Search & indexes

Use **Search & indexes** when views, filters, relations, or searches on a large table become slow. Teable watches the query workload in the background and summarizes each table: how it is searched today, which fields are covered, which physical indexes exist, and how many slow queries it saw recently. Instance administrators configure search coverage, create indexes, and follow the results here.

<Info>Search configuration and index changes run asynchronously as background tasks. Confirm the outcome under **History** after submitting.</Info>

<Info>Query observation is off by default. Set `V2_TABLE_QUERY_OPS_ENABLED` to `true` on the backend and restart to start collecting observations.</Info>

## Find the table to work on

The page opens on the table list. The state buttons across the top carry their own counts and narrow the list:

| State | Meaning |
| --- | --- |
| **All tables** | All undeleted tables in the instance, including tables without query observations yet. |
| **Needs attention** | Tables with slow queries, timeouts or pending recommendations, or configured search that is not serving or does not cover all compatible fields. Start here. |
| **Indexed search** | Tables whose index metadata is published and usable and whose runtime switch is on, so search really runs on the index. |
| **Configured, not serving** | The count is for configured tables still falling back to a full scan. Clicking lists all tables with search configured, so you can compare configuration with serving status. |
| **Unconfigured** | Tables with no search coverage yet. |
| **Unavailable** | Tables that cannot use indexed search right now. The row states why. |

The search box accepts table, Project, and Space names or IDs. Sorting is either **Most slow queries** or **Table name**. **Observation window** covers the last 1 hour or 24 hours, and every observation figure in the list follows that window. Observations are kept for 2 days; anything older no longer appears in the list.

Each row gives the table's estimated rows and size, the requests and slow queries within the window, the current search method and field coverage, the number of filter/sort indexes, and the counts of pending recommendations and active tasks. Click a table name to open its detail.

Use **Choose a table** at the top to switch tables directly. The selected table stays selected when you switch to **Complexity** or **Schema integrity**; **Computed updates** shows the queue for the whole instance.

## Read the index state

The table list and the table detail both show an index state next to the search method:

| State | Meaning | What to do next |
| --- | --- | --- |
| **Not configured** | No saved search configuration and no index metadata. | Choose **Configure search** if the table needs indexed search. |
| **Pending publication** | The configuration is saved; the index is not published yet. | Check **History** for a task still running. |
| **Ready** | The index metadata is published and usable. | Check the actual search method and runtime switch to confirm the index is serving. |
| **Unusable metadata** | The index metadata is broken and cannot serve search. | Run **Update selection / rebuild** again. |

Two lines can appear below the state. **Configured: pg_bigm / pg_trgm** means the saved provider differs from the search method in use, and **Indexed-search runtime switch: off** means the index is ready but the runtime is off, so search still runs `ILIKE`.

When a notice at the top of the page reports tables whose configured search index is not serving, search on those tables falls back to `ILIKE`. If it also says the task worker is off, set `V2_TABLE_QUERY_OPS_TASK_WORKER_ENABLED` to `true` on the backend and restart so the indexes can be rebuilt.

<Info>A published index does not mean every search hits it: a probe that is too short, or a field outside the coverage, still falls back to `ILIKE`. This page reports the state of the index, not proof that recent requests hit it.</Info>

## Configure search coverage

The **Search** tab shows the table's current search method, how many fields are covered, and the **Serving coverage** of each field. **Show uncovered fields** narrows the list to the fields not yet included; fields marked **Not eligible** cannot contribute to a substring search index.

<Info>Serving coverage requires published, usable index metadata and the runtime switch on; a saved configuration alone does not count. Coverage is explicit, so fields you add later are not included automatically; configure the table again to bring them in.</Info>

Choose **Configure search** on a table that has never been configured, or **Update selection / rebuild** on one that has, which opens with the provider and field selection saved last time. The dialog asks for:

| Item | What to enter |
| --- | --- |
| **Search provider** | `pg_bigm` or `pg_trgm`. If the extension is missing, the dialog says what is missing and who can provision it. |
| **Representative search text** | Text your users would really search for. It checks substring semantics and collects plan evidence, and is never saved. If it is too short, the dialog names the minimum length. |
| **Fields** | Select the fields users actually search. Do not select everything on a wide table; building a search document for every field is expensive. |

**Analyze and dry-run** runs the change without committing it and reports the covered field count, estimated rows, whether plan evidence exists, and the impact of creating or rebuilding. Tables estimated at 50,000 rows or more, or of unknown size, also require the maintenance-window acknowledgement. Then choose **Confirm and queue task**.

<Warning>Creating or rebuilding search coverage generates a search column and a GIN index. It can rewrite the whole table and hold locks, and indexed search is briefly interrupted while it runs. Schedule it inside a maintenance window.</Warning>

What the dialog returns is a task receipt, not a result. Close it and follow the task under **History**. Submitting the same change again returns the existing task.

## Manage filter and sort indexes

The **Indexes** tab lists filter/sort and system indexes, with their validity, management status, size and definition. Substring search indexes are listed separately under **Search**.

**Pending actions** holds the system's index recommendations and says whether plan evidence backs each one. **Review index creation** shows the proposed index, the database it runs against, and the evidence; after you confirm, Teable runs `CREATE INDEX CONCURRENTLY` asynchronously. Large tables and tables of unknown size need the maintenance-window acknowledgement here too.

<Info>This page does not delete indexes. Unmanaged and system indexes may protect constraints or serve other workloads, so they are left alone.</Info>

## Diagnose specific queries

When someone reports a slow table and no recommendation covers it, open the **Diagnosis** tab and choose **Analyze queries**. The analysis only reads saved query shapes and available plan evidence; it creates nothing.

The conclusion is one of **Plan-backed index opportunities found**, **No index opportunity confirmed by the available plans**, or **Insufficient evidence**. Insufficient evidence does not mean a sequential scan happened: a slow observation alone does not establish that the access path is at fault. Below it, each affected query is listed with whether it came from real traffic or a saved view configuration, and the estimated plan cost before and after the proposed index (plan cost, not milliseconds).

## Follow the results

The **History** tab holds three parts:

- **Tasks**: background tasks for this table, with status, attempt count, task kind, and failure reason. When a task eventually succeeded after failing, the error is labelled as a prior attempt.
- **Search configuration history**: the provider, status, and field list of each past coverage configuration.
- **Recommendation history**: recommendations that were accepted, dismissed, or superseded.

History loads only the most recent entries; when there are more, a line above the list gives the total.

<Info>While a table has a queued or running task, the buttons for configuring search and creating indexes stay disabled. Wait for the task to finish.</Info>

## Assess change impact

Updating records can trigger further calculations in formulas, lookups and rollups through linked records. To assess whether a batch write, field conversion or field deletion could affect a large amount of data, open **Complexity** and select a table, or click **Assess complexity** in its search and index details.

The **Impact matrix** estimates updates, field deletions and conversions for each field, plus record creation and deletion separately. The dot on the left shows the typical case; the fill shows the worst case. Click a cell for affected row estimates, propagation paths, limitations and recommendations. Review **High** or **Critical** changes first to decide whether to reduce batch sizes or adjust calculation dependencies.

In **Estimate settings**, set **Records per change** to the number you plan to submit at once; leaving it empty estimates one record. **Use catalog statistics** is on by default and reads table sizes and link counts from the database to improve the estimate.

<Info>Assessment reads structure and statistics only. It performs no record or field changes and does not predict elapsed time. If a result is **Not estimated** or its quality is **Partial** or **Truncated**, read the limitations and fill the information gaps before deciding. A missing estimate does not mean there is no risk.</Info>
