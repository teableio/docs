<Tip>Доступно для самостоятельного развертывания на тарифе Business и выше</Tip>

Путь: Системное администрирование → JWT credentials (учётные данные JWT)

Приложения, созданные в [App Builder](/ru/basic/ai/app-builder), хранят два вида долгоживущих учётных данных: токен доступа Teable, сохранённый в приложении, и ключ доступа к ИИ, который записывается в его среду выполнения при развёртывании. Оба подписаны секретом подписи JWT (`BACKEND_JWT_SECRET` или `SECRET_KEY`, если тот не задан). После смены этого секрета приложению нужны новые учётные данные, чтобы и дальше обращаться к Teable. Эта страница делает это массово.

## Когда использовать

- Изменился секрет подписи JWT. Сюда относится и удаление `BACKEND_JWT_SECRET`, чтобы он следовал за `SECRET_KEY`, и смена самого `SECRET_KEY`. Порядок шагов см. на странице [Конвергенция секретов](/ru/deploy/secret-convergence).
- Переменные в окружении развёртывания приложения могли утечь, и его ключ доступа к ИИ нужно аннулировать.

## Состояние каждого приложения

Для каждого приложения в списке показано, подписан ли его токен Teable текущим секретом или старым, состояние публикации, время последнего развёртывания и время истечения его ключа ИИ. Фильтруйте с помощью вкладок вверху:

| Вкладка | Какие приложения в ней |
|---|---|
| Needs attention (требуют внимания) | Токен Teable подписан не текущим секретом |
| Live credentials outdated (учётные данные работающего приложения устарели) | Учётные данные заменены, но приложение не было повторно развёрнуто, поэтому работающее приложение всё ещё использует старые, которые больше не действуют |
| Refresh failed (не удалось обновить) | Последнее обновление не удалось |
| Published (опубликовано) / Unpublished changes (неопубликованные изменения) / All (все) | По состоянию публикации |

## Обновление учётных данных после смены секрета

1. При смене секрета поместите старое значение в `BACKEND_JWT_SECRET_OLD`. Тогда существующие токены остаются действительными, пока обновление не завершится. Не задавайте его, если старое значение публично или утекло: значение в `_OLD` по-прежнему принимается, поэтому подделанные с его помощью токены продолжали бы работать. В этом случае приложения не могут обращаться к Teable, пока не будут обновлены, поэтому выполните обновление сразу после перезапуска.
2. На вкладке **Needs attention** выберите все приложения, нажмите **Refresh app credentials** (обновить учётные данные приложений) и отметьте только **Teable access token** (токен доступа Teable).
3. Дождитесь, пока очередь завершится. Опубликованное приложение получает новый токен и повторно развёртывается, когда подходит его очередь, и попутно ключ ИИ в работающем приложении подписывается новым секретом. Неопубликованное приложение получает новый токен, и его запущенный предварительный просмотр подхватывает этот токен на месте.
4. Удаляйте `BACKEND_JWT_SECRET_OLD` только после того, как вкладки **Needs attention**, **Refresh failed** и **Live credentials outdated** все опустеют. Для приложений на двух последних используйте **Refresh app envs** (обновить окружения приложений).

Teable хранит токен каждого приложения зашифрованным с помощью ключа, производного от секрета подписи JWT. Когда старое значение удалено, приложение, до которого обновление не дошло, перестаёт работать; обновление его токена возвращает его в строй.

Чего ожидать во время обновления:

- Каждое опубликованное приложение повторно развёртывается один раз, и его запросы завершаются ошибкой только на время его собственного повторного развёртывания.
- У приложения с неопубликованными изменениями повторно развёртывается опубликованная версия, а неопубликованные изменения остаются как есть.
- Вход посетителей в приложении с включённым входом сбрасывается, потому что сеансы приложения подписаны этим токеном.

Если переменные в окружении развёртывания могли утечь, отметьте также **AI access key** (ключ доступа к ИИ). Старый ключ сразу перестаёт действовать, включая копии в локальном `.env` владельца и в скачанном коде.

## Распределение повторных развёртываний

Провайдеры развёртывания обычно ограничивают число развёртываний, которые может запустить одна учётная запись. Если отмечен флажок **Spread out the redeploys** (распределить повторные развёртывания), повторные развёртывания запускаются пакетами по временным окнам, и в каждом окне запускается не больше заданного вами числа. Страница сообщает, когда примерно запустится последний пакет.

По умолчанию каждый сервер повторно развёртывает по одному опубликованному приложению за раз. Если приложений много, задайте переменную окружения `APP_ENV_REFRESH_CONCURRENCY` (по умолчанию `1`), чтобы ускорить процесс, — ценой того, что на каждом сервере одновременно будет выполняться столько же сборок.

## Приложения, у которых работающая версия не обновилась

С приложениями на вкладке **Live credentials outdated** можно поступить двумя способами:

- **Refresh app envs** пересобирает на месте работающую среду выполнения опубликованного приложения с текущим токеном Teable и заново подписанным ключом ИИ. Новая версия не создаётся, и владельца приложения это не затрагивает.
- **Check with deploy provider** (сверить с провайдером развёртывания) — для приложений, которые вы уже повторно развернули у провайдера. Это действие читает, когда было собрано работающее развёртывание и когда в последний раз обновлялись переменные с учётными данными, и убирает с этой вкладки приложения, у которых подтверждено, что новые учётные данные уже работают. Оно только читает: ничего повторно не развёртывается, и значения переменных не читаются. Пока поддерживаются только приложения, развёрнутые на Vercel.
