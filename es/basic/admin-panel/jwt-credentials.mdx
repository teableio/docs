Ruta: Administración del sistema → Credenciales JWT

Las aplicaciones creadas con [App Builder](/es/basic/ai/app-builder) tienen dos credenciales de larga duración: el token de acceso de Teable almacenado en la aplicación y la clave de acceso a la IA que se escribe en su entorno de ejecución cuando se despliega. Ambas se firman con el secreto de firma de JWT (`BACKEND_JWT_SECRET`, o `SECRET_KEY` cuando aquella no está establecida). Después de que ese secreto cambie, una aplicación necesita credenciales nuevas para seguir accediendo a Teable. Esta página lo hace en bloque.

## Cuándo usarla

- El secreto de firma de JWT ha cambiado. Esto incluye eliminar `BACKEND_JWT_SECRET` para que siga a `SECRET_KEY`, y cambiar la propia `SECRET_KEY`. Consulta [Convergencia de secretos](/es/deploy/secret-convergence) para conocer el orden de los pasos.
- Las variables del entorno de despliegue de una aplicación pueden haberse filtrado, y hay que invalidar su clave de acceso a la IA.

## Ver el estado de cada aplicación

Para cada aplicación, la lista muestra si su token de Teable se firmó con el secreto actual o con el anterior, su estado de publicación, cuándo se desplegó por última vez y cuándo caduca su clave de IA. Filtra con las pestañas de la parte superior:

| Pestaña | Aplicaciones que contiene |
|---|---|
| Requieren atención | El token de Teable no se firmó con el secreto actual |
| Credenciales publicadas desactualizadas | Las credenciales se sustituyeron pero la aplicación no se volvió a desplegar, por lo que la aplicación en vivo sigue usando las anteriores, que ya no funcionan |
| Error de actualización | La última renovación no se completó correctamente |
| Publicadas / Cambios sin publicar / Todas | Por estado de publicación |

## Renovar las credenciales tras un cambio de secreto

1. Cuando cambies el secreto, pon el valor anterior en `BACKEND_JWT_SECRET_OLD`. Así, los tokens existentes siguen siendo válidos hasta que termine la renovación. No lo pongas si el valor anterior es público o se ha filtrado: un valor en `_OLD` se sigue aceptando, por lo que los tokens falsificados con él seguirían funcionando. En ese caso, las aplicaciones no pueden acceder a Teable hasta que se renueven, así que hazlo justo después del reinicio.
2. En **Requieren atención**, selecciona todas las aplicaciones, haz clic en **Renovar las credenciales de las aplicaciones** y marca solo **Token de acceso de Teable**.
3. Espera a que termine la cola. Una aplicación publicada recibe un token nuevo y se vuelve a desplegar cuando le llega el turno, y de paso su clave de IA en vivo se firma con el secreto nuevo. Una aplicación no publicada recibe un token nuevo, y su vista previa en ejecución lo adopta sobre la marcha.
4. Elimina `BACKEND_JWT_SECRET_OLD` solo después de que **Requieren atención**, **Error de actualización** y **Credenciales publicadas desactualizadas** estén todas vacías. Usa **Actualizar los entornos de las aplicaciones** para las aplicaciones de las dos últimas.

Teable almacena el token de cada aplicación cifrado con una clave derivada del secreto de firma de JWT. Una vez desaparecido el valor anterior, una aplicación a la que la renovación no haya llegado deja de funcionar; renovar su token la recupera.

Qué esperar durante una renovación:

- Cada aplicación publicada se vuelve a desplegar una sola vez y sus solicitudes fallan solo mientras dura su propio redespliegue.
- En una aplicación con cambios sin publicar, se vuelve a desplegar la versión publicada y los cambios sin publicar se quedan como están.
- A los visitantes de una aplicación con el inicio de sesión activado se les cierra la sesión, porque las sesiones de la aplicación se firman con este token.

Si las variables de un entorno de despliegue pueden haberse filtrado, marca también **Clave de acceso a la IA**. La clave anterior deja de funcionar de inmediato, incluidas las copias del `.env` local del propietario y las del código descargado.

## Escalonar los redespliegues

Los proveedores de despliegue suelen limitar cuántos despliegues puede iniciar una cuenta. Con **Escalonar los redespliegues** marcado, los redespliegues se inician por lotes según ventanas de tiempo, y en cada ventana se inicia como máximo el número que establezcas. La página te indica aproximadamente cuándo se inicia el último lote.

De forma predeterminada, cada servidor vuelve a desplegar una aplicación publicada a la vez. Si hay muchas aplicaciones, establece la variable de entorno `APP_ENV_REFRESH_CONCURRENCY` (valor predeterminado: `1`) para ir más rápido, a costa de que en cada servidor se ejecute a la vez ese mismo número de compilaciones.

## Tratar las aplicaciones que no se han actualizado en vivo

Hay dos formas de tratar las aplicaciones de **Credenciales publicadas desactualizadas**:

- **Actualizar los entornos de las aplicaciones** reconstruye in situ el entorno de ejecución en vivo de una aplicación publicada, con el token de Teable actual y una clave de IA recién firmada. No crea ninguna versión nueva y no afecta al propietario de la aplicación.
- **Comprobar con el proveedor de despliegue** es para las aplicaciones que ya has vuelto a desplegar en el proveedor. Lee cuándo se compiló el despliegue en vivo y cuándo se actualizaron por última vez las variables de credenciales, y saca de esta pestaña las aplicaciones cuyas credenciales nuevas se confirma que están en vivo. Solo lee: no se vuelve a desplegar nada y no se lee el valor de ninguna variable. Por ahora solo se admiten las aplicaciones desplegadas en Vercel.
