<Tip>Disponible avec le forfait Business auto-hébergé et les forfaits supérieurs</Tip>

Chemin : Administration système → Rotation des clés → JWT credentials (identifiants JWT)

Les applications créées avec [App Builder](/fr/basic/ai/app-builder) détiennent deux identifiants de longue durée : le jeton d’accès Teable stocké sur l’application, et la clé d’accès à l’IA écrite dans son environnement d’exécution lors de son déploiement. Tous deux sont signés avec le secret de signature JWT (`BACKEND_JWT_SECRET`, ou `SECRET_KEY` lorsque celui-ci n’est pas défini). Après un changement de ce secret, une application a besoin de nouveaux identifiants pour continuer d’accéder à Teable. Cette page le fait en masse.

## Quand l’utiliser

- Le secret de signature JWT a changé. Cela inclut la suppression de `BACKEND_JWT_SECRET` pour qu’il suive `SECRET_KEY`, ainsi que le changement de `SECRET_KEY` lui-même. Consultez [Convergence des secrets](/fr/deploy/secret-convergence) pour l’ordre des étapes.
- Des variables de l’environnement de déploiement d’une application ont pu fuiter, et sa clé d’accès à l’IA doit être invalidée.

## Voir où en est chaque application

Pour chaque application, la liste indique si son jeton Teable a été signé avec le secret actuel ou avec l’ancien, son état de publication, la date de son dernier déploiement et la date d’expiration de sa clé IA. Filtrez à l’aide des boutons au-dessus de la liste :

| Filtre | Applications qu’il contient |
|---|---|
| Needs attention (à traiter) | Le jeton Teable n’a pas été signé avec le secret actuel |
| Live credentials outdated (identifiants en ligne obsolètes) | Les identifiants ont été remplacés mais l’application n’a pas été redéployée ; l’application en ligne utilise donc encore les anciens, qui ne fonctionnent plus |
| Refresh failed (échec de l’actualisation) | La dernière actualisation n’a pas abouti |
| Published (publiées) / Unpublished changes (modifications non publiées) / All (toutes) | Par état de publication |

## Actualiser les identifiants après un changement de secret

1. Lorsque vous changez le secret, placez l’ancienne valeur dans `BACKEND_JWT_SECRET_OLD`. Les jetons existants restent alors valides jusqu’à la fin de l’actualisation. Ne le faites pas si l’ancienne valeur est publique ou a fuité : une valeur placée dans `_OLD` est toujours acceptée, et les jetons fabriqués avec elle continueraient donc de fonctionner. Les applications ne peuvent alors pas accéder à Teable tant qu’elles n’ont pas été actualisées ; faites-le donc juste après le redémarrage.
2. Sous **Needs attention**, sélectionnez toutes les applications, cliquez sur **Refresh app credentials** (actualiser les identifiants des applications) et cochez uniquement **Teable access token** (jeton d’accès Teable).
3. Attendez que la file d’attente soit entièrement traitée. Une application publiée reçoit un nouveau jeton et est redéployée lorsque son tour arrive, et sa clé IA en ligne est signée au passage avec le nouveau secret. Une application non publiée reçoit un nouveau jeton, et son aperçu en cours d’exécution l’adopte sur place.
4. Ne supprimez `BACKEND_JWT_SECRET_OLD` qu’une fois **Needs attention**, **Refresh failed** et **Live credentials outdated** tous vides. Utilisez **Refresh app envs** (actualiser les environnements des applications) pour les applications des deux derniers.

Teable stocke le jeton de chaque application chiffré avec une clé dérivée du secret de signature JWT. Une fois l’ancienne valeur supprimée, une application que l’actualisation n’a pas atteinte cesse de fonctionner ; l’actualisation de son jeton la rétablit.

À quoi vous attendre pendant une actualisation :

- Chaque application publiée est redéployée une seule fois, et ses requêtes n’échouent que pendant son propre redéploiement.
- Pour une application comportant des modifications non publiées, c’est la version publiée qui est redéployée, et les modifications non publiées restent telles quelles.
- Les visiteurs d’une application dont la connexion est activée sont déconnectés, car les sessions de l’application sont signées avec ce jeton.

Si des variables d’un environnement de déploiement ont pu fuiter, cochez également **AI access key** (clé d’accès à l’IA). L’ancienne clé cesse aussitôt de fonctionner, y compris les copies présentes dans le fichier `.env` local du propriétaire et dans le code téléchargé.

## Étaler les redéploiements

Les fournisseurs de déploiement limitent généralement le nombre de déploiements qu’un compte peut lancer. Lorsque **Spread out the redeploys** (étaler les redéploiements) est coché, les redéploiements démarrent par lots, par fenêtre de temps, chaque fenêtre en lançant au maximum le nombre que vous avez défini. La page vous indique approximativement quand le dernier lot démarre.

Par défaut, chaque serveur redéploie une seule application publiée à la fois. Si les applications sont nombreuses, définissez la variable d’environnement `APP_ENV_REFRESH_CONCURRENCY` (`1` par défaut) pour aller plus vite, au prix d’autant de builds exécutés simultanément sur chaque serveur.

## Traiter les applications non mises à jour en ligne

Il existe deux façons de traiter les applications figurant sous **Live credentials outdated** :

- **Refresh app envs** reconstruit sur place l’environnement d’exécution en ligne d’une application publiée, avec le jeton Teable actuel et une clé IA nouvellement signée. L’opération ne crée aucune nouvelle version et n’affecte pas le propriétaire de l’application.
- **Check with deploy provider** (vérifier auprès du fournisseur de déploiement) est destiné aux applications que vous avez déjà redéployées chez le fournisseur. L’opération lit la date de build du déploiement en ligne et la date de dernière mise à jour des variables d’identifiants, puis retire de ce filtre les applications dont les nouveaux identifiants sont confirmés en ligne. Elle se limite à la lecture : rien n’est redéployé et aucune valeur de variable n’est lue. Seules les applications déployées sur Vercel sont prises en charge pour le moment.
